> 这份笔记是我读 `../mcloud-back/internal/app/live_room*.go`（三家共 1336 行）后提炼的
> **判据级**要点。任务描述里没展开的细节在这里，动笔前读一遍。
> 所有条目都有原实现的注释支撑，不是我的推断。

## 1. 四态结论模型（`RunReport`）—— 照抄它，别自己发明

| 情形 | 结论 |
|---|---|
| **没领**（门没开 / 一个口令都没收到） | **成功** |
| 领了、**一个都没成** | **失败** |
| 领了、成了**一部分** | **部分成功** |
| 领了、全成 | 成功 |

⚠ 「没领 ⇒ 成功」的理由：「今天没开播」是**正常结果**（与签到里"今天已经签过了"同一档），
不是失败。但**失败**那一档不是"没跑到"，是"目标没达成"，所以小结里必须带原因
（无效 / 已兑换 / 未分类），不能只剩一个光秃秃的"失败"。

⚠ 原实现刻意**不放** `ManualStep`（"要人去客户端点一下"）—— 这条链上没有这种动作。

## 2. 三种"没领"必须分开说（`idleSummary`）

> ⚠ 2026-10-01：原来这里还有第四种"获取口令但不领取"（`koulingOnly`）。
> 那条开关被用户判为**伪需求**并已删 —— 它与"边听边领"直接矛盾
> （抓取的价值就在于当场把口令验成有效），文案还是从 CLI 搬来的
> （"打印"在浏览器里没有对应物）。删掉之后"没领"只剩下面两种+"开门了但没收到"。

```
门没开 & LiveCount==0 → "今天没有直播，没有口令可收"        （下一步：等）
门没开 & LiveCount>0  → "有 N 间在播，但没有一间是「中国移动云盘」"（下一步：别等了）
开了门但没收到        → "开了门但没收到口令"
```

⚠ 混成一句"没有可领的口令"会让人去查**收集**那一步，而那一步根本没被走到过。
`LiveCount` 这个字段存在的**唯一理由**就是区分前两种。

## 3. 进账用**两次读数相减**，不是把每个口令的 `flowerNum` 加起来

```
进账 = ⑥BalanceAfter.FlowerCnt − ①BalanceBefore.FlowerCnt
```

⚠ 理由：相加会**漏掉③首次参与惊喜奖**那几朵，而它不在任何一个口令的结果里
—— 那正好是"总数对不上"这类问题最常见的来源。**这条务必有测试。**

## 4. 口令结果要分**四类**，不是"成功/失败"两类

| 类别 | 判据 | 进不进重试排除表 | 用户可见措辞 |
|---|---|---|---|
| 成功 | `code==0` 且有 `result` | — | 获得 N 朵 |
| **无效口令** | `200108`（需当场直播获取） | ✅ **进** | "无效口令 X" |
| **已兑换** | `200112` | ✅ 进（因为已试过） | "已兑换过" |
| **口令已失效** | `200118`（**本场已结束**） | ❌ **不进** | "口令已失效（本场已结束）" |
| **未分类** | 其它数字码 | ✅ 进 | "未分类口令 X" |
| 解析失败 | 响应不像信封 | ❌ 不算无效 | warn，跳过 |

⚠⚠ **`200118` 必须单独一栏**，因为它是**用户可见的那句话**：它最常见的成因是
**"直播已经结束了"**，而"未分类口令"这个词会把人往**"口令抄错了"**那边引
—— 排查方向一开始就错（原项目坑表 **#140**）。
⚠ 它**不是**无效口令：口令本身是**对的**，所以**不触发**那次 60 秒重听（重听也只会再拿一次 200118）。

## 5. 重试逻辑（`RetryPlan` / `PickNewCodes`）—— 两个容易写错的边界

```rust
retry  = !invalid_codes.is_empty()          // 没有无效口令就**不重听**
exclude = merge(first_batch, invalid_codes) // 重听时排除「已试过的」
```

⚠ 边界一：**没有无效口令就不重听** —— 一次完全正常的运行不该多听 60 秒。
⚠ 边界二：**必须排除"第一次就成功的"**。不排除的话第二轮会把同一批口令再领一遍，
而**同一账号**对同一条**正确**口令的第二次请求会回 `200112`（已兑换）——
它不是新结果，却会污染归因，看起来像"口令坏了"。
⚠⚠ 这个理由**不是**"口令会被消耗"（口令全场通用，见文件头五条事实②）。
**不要把"消耗"这个概念写进代码或注释。**

## 6. 埋点埋 5 条，但**实拍只证实了 1 条**

```
National_LiveRoomFeedback_pv / _client / _client_isApp / _login / _flowerBtn
```

⚠ 实拍抓到的只有最后一条（点按钮那一刻发的）；其余四条在真实客户端里属于**页面加载期**，
本轮抓包窗口里没出现。**为什么还是照发全 5 条**：它们是服务端活动系统的"到场"证据，
"是不是必发"**没有证据**，而两边代价不对称 —— 多发 4 个请求 = 一点噪声；
少发 = 可能整条抽奖链被**静默拒掉**，而那时的表现是 `200108`，看起来像"口令抄错了"，
会把人引到完全错误的方向。⇒ 照抄原项目，**并把这句"未验证"写进注释**。

⚠ 埋点的**响应不解析**：它是"到场"证据，回什么码都不改变后面的步骤。
拿它当门槛会让"埋点接口偶发 5xx"变成整条链失败，而它本来只是噪声。

## 7. 只听**第一间**房间 —— 是刻意的取舍，不是漏了循环

原项目 `for (const room of rooms)` 会把该主播**每一间**在播房间都听一遍。
原实现只取 `Rooms[0]`：同时开两间以上是少数情况，而顺序听 N 间会把墙钟变成
`N × ListenSeconds`（默认 60s ⇒ 3 间就是 3 分钟）。

⚠ **代价必须说出来**：同时开两间时，第一间之外的口令会被**整场漏掉**。
所以**只要房间数 > 1 就必须 warn**（`LevelWarn`），否则用户看到"在播房间 X，听 60 秒"
会以为已经听全了。

## 8. 票的来源：**云盘侧**，不是直播侧（这是实打实踩过的坑）

六步链全打在 `m.mcloud.139.com/ycloud`（与签到同域同族），要的 `jwttoken` 是
**云盘侧 `tyrzLogin` 那一份**，**不是**开门换到的直播侧 JWT
—— 拿后者去读，实测回 **`90001 未登录`**（2026-09-22 两个账号都是这句）。
⇒ 会话要用**签到页那套配方**（`jwttoken 使用公共来源`），并在注释里留这句痕。

⚠ 建会话的位置：**在领取之前**，不是开门之前。理由：SSO token 很短命
（换完几十秒内就要用），而中间夹着一整段听弹幕（默认 60 秒）。
放在领之前才是"拿到口令 → 立刻用它"。

## 9. 错误要带**步名**

六步里 ①②⑥ 用的是同一个 `user/info`，而②会发 5 次 —— 不带步名的错误
（"user/info 响应没有 result"）会让人分不清是**起始余额**还是**终值**。
⇒ 错误前缀形如 `[user_info_before]`。

## 10. 解析失败要**中止**，不要跳过

六步每一步的响应都带着后面要用的信息（余额、判定）。解析失败意味着
"上游换了信封形状"或"我们打错了端点"，继续跑只会把同一个问题重复六遍，
而且日志里看不出是哪一步开始的。⇒ 中止 + 原样带回错误，排查面最小。

⚠ 但**复活花（⑤）是唯一例外**：它拿不到不该让整条链失败 —— 六步里只有它纯属
"顺便看一眼"。留 0 并继续。

## 11. 写请求的重放边界（要如实标注为**待验证**）

唯一会被重放的写请求是 `draw`（第④步）。重放只在 `90001 未登录` 时发生 ——
那一次的响应说明服务端**没有**受理这条口令。而"票过期发生在服务端受理之后"
这种情形**没有样本**，属**待验证**。⇒ 注释里如实写，别写成"安全"。

## 12. 参数校验（`LiveRoomParams::Check`）—— 判据在本层，措辞在各调用方

```
SkipKouling && codes.is_empty() → 关掉了唯一来源又没给手工口令
ListenSeconds <= 0             → **任何**情况下都非法（不看 SkipKouling）
```

⚠ 判据只在**一处**（否则两处漂移，没人能读出哪个对）；措辞必须在**各调用方各写一遍**
（CLI 要说 `--skip-kouling`，服务端要说"关掉了唯一的弹幕来源"，
把 flag 名塞进领域层会让界面上输出一句没有 flag 的话）。

## 13. 产品事实（写进注释，别当提示文案）

- **`--codes` 不是可选项**：小红书那条口令没法自动化（那边无法鉴权），
  必须人工喂进来。这就是为什么"听弹幕"永远拿不全两条。
- **任何"历史口令"都是废值**：口令只在**本次直播**有效，上一场的不能用。
  ⇒ 不要保存口令、不要跨场复用、**不要拿已结束场次的弹幕当口令来源**。
- 口令**全场通用**：不存在"消耗口令"这件事。
- 每场 **2~3 条**是正常形状：别把"只收到 1 条"当成已收全，也别把"收到 3 条"当脏数据。
- 弹幕里的口令**署名是谁都能用**：别按"发信人是不是我"过滤。
