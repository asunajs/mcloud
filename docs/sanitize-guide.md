这份文档给**写抓包/协议文档的人**看：把上游协议记录下来很有价值，但里面的真实值一旦进版本库就收不回来。
仓库是 private 也不等于安全 —— 值进了历史，之后转公开、加协作者、泄露本地克隆，都是不可控的。

门禁命令（提交前必跑，输出非 0 就是没脱干净）：

```bash
node scripts/check-identifiers.cjs
```

它会扫「已跟踪 + 未跟踪但未忽略」的文本文件，**并且把 base64 载荷解码后再扫一遍**（`auth` 这类是 base64，字面扫描看不见里面的号码）。

## 一、脱敏的目标：**换值不换形**

真实值必须换掉，但**协议的形状信息必须留下** —— 否则这份文档就没用了。

| 类别 | 怎么换 | 改后长什么样 |
| --- | --- | --- |
| 手机号 | `199` 号段的**等长**值 | 11 位号码 → `19900000000` |
| `userDomainId` | 19 位、`199` 开头（等长） | 19 位标识 → `1990000000000000001` |
| 口令散列 / 随机凭据 | **等长**合成值（保持字符集） | 32 位大写十六进制 → 32 个 `A` |
| `authToken` 这类结构化 token | **保留分段与长度**，只替换载荷字符 | 见下 |

> **本文件刻意不写"改前"的真实值** —— 连示例都不写，否则这份 SOP 自己就会触发守卫
> （`scripts/check-identifiers.cjs` 的注释里记着同一个教训：那个脚本第一版就是被自己抓到的）。

`authToken` 的正确处理（这是本仓库踩过的坑）：形状是
`<前缀>|1|RCS|<13 位毫秒>|<载荷，以 _ 与 . 分段>`，处理时**只换字符、不换结构**：

```
改后（202 字符）：SYNTH001|1|RCS|1792245335331|AA…A.AA…
                   ↑ 分段数、各段长度、_ 与 . 的位置与原值完全一致
```

分段数、各段长度、`_` / `.` 的位置全部一致，读者照样能知道 token 长什么样、怎么切分。

**什么算过度脱敏**（同样要避免）：

- 把整段值换成 `<REDACTED>` —— 长度、分段、字符集的信息全丢了，文档不再能用来写实现
- 把请求/响应样本删掉只留字段名 —— 协议文档的价值就是**真实的报文形状**
- 连带把时间戳（13 位毫秒）、`random`、错误码也抹掉 —— 它们不是凭据，抹了只损失信息
- 因此：**明显是占位的值不会被守卫报**（含 `REDACTED`/`SYNTH`/`EXAMPLE` 等关键词、整值同字符重复、去分隔符后字符种类 ≤ 4、含非 ASCII 的中文说明、或没有任何一段 ≥16 字符的不透明长串）

**可以保留的**：

- 字段名、长度、时序、错误码、状态机取值
- 13 位毫秒时间戳、`random` 挑战值、已失效的一次性验证码（后者用于说明字段内容）
- 上游客户端源码素材（见下）

## 二、上游源码素材按来源豁免

`docs/capture/apiServer.js` 与 `docs/capture/pcclient-api.js` 是**移动客户端源码**
（用于对照协议实现），不是本项目的产出、也不是用户数据。
它们里面的号码之类是上游自带的调试残留，脱敏只会毁掉这份对照素材，所以按**来源**豁免
（`VENDOR_SOURCE_PATHS`），**不是**把这些值登记进 `ALLOWED` —— 那等于承认"这是要留在仓库里的真实标识"，
与"真实值一律不准登记"冲突。

> **新增抓包素材时要逐个判断，不要因为"在 `capture/` 目录下"就默认安全。**
> 这个清单漏过 `pcclient-api.js` 一次 —— 它是 `app.asar` 里 `apiServer.js` 的姊妹文件，
> 当时没被报出来纯属**恰巧**不含真实标识。

反过来也要注意：**别把用户数据往 vendored 素材里塞**（例如调试时把自己的号码写进注释），那会绕过这道闸。

## 三、真实值已经提交了怎么办：**改写历史**，不要追加修复提交

追加一个"脱敏"提交**不解决问题** —— 值仍然留在之前的提交里，`git log -p` 就能翻到。

```bash
# 1. 先在工作区把值改掉并确认守卫通过
node scripts/check-identifiers.cjs

# 2. 把它并入引入它的那个提交（不是新增提交）
git add <改动过的文件>
git commit --amend --no-edit          # 或 --amend 后改提交信息

# 3. 强推（带 lease：远端不是预期的提交就拒绝，避免覆盖别人的新提交）
git push --force-with-lease=main:<改写前远端那个 SHA> origin main
```

**改写后要通知协作者重新拉取**（他们的本地分支会和改写后的历史分叉）：

```bash
git fetch origin && git reset --hard origin/main
```

> 强推会让旧提交从分支上消失，但 GitHub 仍可能按 SHA 缓存一段时间。所以**别指望"先推上去再改写"** ——
> 提交前跑一次守卫，成本远低于事后重写。

## 四、几个容易漏的点

- **CSV 里的 JSON 是双引号转义的**（`""dycpwd"":""…""`）。守卫会额外扫一遍反转义后的文本，你自己肉眼审时也要注意
- **守卫报告里的凭据是掩码**（`前6…后4`）：定位用前 6 个字符 `grep` 即可，它**故意不打印完整值**（报告要落进日志与终端回滚缓冲，抄一遍等于又泄一次）
- **只改一半不算改**：曾经出现过"在 token 中间插一个 `.` 就算打码"的情况 —— 值仍然完全可用。判断标准是**原值不能再被恢复出来**
- **提交信息、分支名、PR 描述也要一起检查** —— 守卫只扫**文件内容**，看不到 commit message。
  改文件时把真实值顺手抄进 commit message 或代码注释，一样会留在历史里。
  自查用 `git log -S'<前几个字符>' --oneline`：**能搜出来就是没改干净**（改完记得连提交信息一起 `--amend`）
- 抓包原始素材（HAR、请求样本）本身含凭据：`har/`、`*.har` 已在 `.gitignore`；要入库的样本必须先过守卫
