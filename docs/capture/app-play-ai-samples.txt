## 2. 本族请求头**比仓库其余 H5 接口少两个**（实拍裁出来的，不是脱敏）

六条 `newyear/*`（第 4/5/7/10/11/12 条）的头名并集，去掉 HTTP/2 伪头后是：

```
accept  accept-encoding  accept-language  cookie(多条)  jwttoken  referer
sec-fetch-dest  sec-fetch-mode  sec-fetch-site  showloading  user-agent
content-type  origin            ← 只有两条 POST（第 7/12 条）有
```

- **没有** `appversion`、**没有** `activityid`、**没有** `deviceid`（**头名**都没有，不是值被抹）。
- **对照**（同一份归档，所以能排除"归档器抹头名"）：第 **0/1/2/3** 四条**三条都带**，
  逐条数过：`appversion` + `activityid` + `deviceid` 全在。⇒ 是这一族**真的没发**。
- 两条 POST 的 `content-type` 逐字 `application/json;charset=UTF-8`，`origin` 逐字
  `https://m.mcloud.139.com`；**GET 一条都不带 `origin`** ⇒ 不"顺手统一"。
- ⚠ 本仓的 `WithH5Headers` 会加 `activityid` + `appversion`（它**也不发** `deviceid`，
  那一个是 `FunaiModuleRequest` 一类调用点自己补的）⇒ 所以这一族不复用它，
  另写一份 `playAIH5Headers`。代价：这一族的头集合单独维护一处。
- ⚠ 反过来"上游会不会因为少/多这些头而改变判断"**未测试** —— 本层只钉"发出去的这一组恰好是这些"。

## 3. `jwttoken` 的来源（`AGENTS.md` §1.12 证据侧要求：必须记）

- **实拍面**：六条 `newyear/*` 条条带 `jwttoken`，**值全部 `<REDACTED>`**；
  整份归档里 `querySpecToken` / `tyrzLogin` / `marketName: shake_shake` / `sourceId: 1314`
  **grep 零命中**（连 body 里都没有）⇒ **归档没有换票那一步**，这一页的票是**从哪来的**没有实拍答案。
- **出处面**（本轮新核到，2026-09-24）：旧 TS **有**这一页自己的两步 ——
  `packages/core/src/tasks/play-ai-special/task.ts:50-70` 调 `apis/auth.ts:61-97`：

  ```
  ① GET  https://m.mcloud.139.com/ycloud/api/cloud/userdomain/v2/querySpecToken
          ?targetSourceId=001005&hideLoading=true            ← 带四个签名头
  ② POST https://m.mcloud.139.com/ycloud/auth-service/auth/tyrzLogin
          body {token:<①的 result>, openAccount:false, marketName:"shake_shake",
                sourceId:"1314", type:"signupPlatform", channel:null}
          头另加  type: signupPlatform                        ← result.token 就是这一页的 jwttoken
  ```

- ⚠ 本仓**已有同一个端点**（`TyrzLoginRequest` / `TyrzLoginBody`，`app_signin_session.go:114-147`），
  但**参数不同**：签到那一份 body 是 `{marketName, openAccount:0, sourceId, token}` 四键
  （`openAccount` 是**数字** `0`，旧 TS 这一页是**布尔** `false`），没有 `type` / `channel`，也不带 `type` 头。
  而 ① 那一条（**GET** 的 `querySpecToken`）与本仓已实现的（**POST** `querySpecTokenV2`，
  域名 `user-njs.yun.139.com`）是**两个不同端点**。⇒ 正是 §1.12 事实②那种"URL 相同而参数不同 / URL 相近而端点不同"。
- **当前实现取态**：上面那两步**已经实现成代码**（`app_play_ai_session.go` 的
  `PlayAIQuerySpecTokenRequest` → `PlayAITyrzLoginRequest` → `PlayAISession`，32 条用例），
  但**实现的依据是旧 TS 字面量，本归档仍零条支持那两步的参数与头** ⇒ 它属于"有出处、无实拍"，
  不是"实测过能过"。①…⑤ 这一族的 `jwt` 仍由调用方注入（**公共来源**，§1.12 临时态）；
  "真打之前要不要改用它建这一页自己的票" = **待用户拍板**（`docs/pending-decisions.md` **P5**）。
  ⚠ 反过来：抓到那两条实拍 ⇒ 这一格才从"待拍板"变成"可切换"，届时按 §1.12 主动更正。

## 4. ⑤ `aiRecognize` 这一条（形状最贵的一条）

- **域与头**：`https://ai.yun.139.com`，走**原生那套**（`Authorization` + `x-yun-tid` + `x-DeviceInfo`
  + `x-yun-api-version`），**不带** `jwttoken`、**不带** `showloading`；
  `Origin: mcloudlocal://yun.139.com`；`Content-Type: application/json`（⚠ **无 charset**，
  与 `newyear/*` 那两条 POST 的 `application/json;charset=UTF-8` 不同 ⇒ 本层先剥后补，逐字按实拍）。
- **body 八键逐字**：`base64`（值是**整条 data URL**：`data:image/jpg;base64,<REDACTED>`，
  ⚠ 不是裸 base64 ⇒ 不拼前缀也不剥前缀）、`channelId:"101"`、`imageExt:"jpg"`、`recognizeType:"1"`、
  `sendType:"2"`、`timeout:30000`（**数字**）、`uploadToCloud:true`（**裸布尔**）、
  `userId:"<19 位标识>"`（账号标识，**不是**凭据；本仓测试用 `199…` 合成号）。
- `Content-Length: 80773` ⇒ 那一次传的是**一张真实照片**（几十 KB base64）。
- **设备画像矛盾**（§5.6 那条在这里就看得见）：`User-Agent` 是 **iPad** WebKit，
  而 `x-DeviceInfo` 与 `x-yun-client-info` 按旧 TS 写的是 **iPhone / `ios 18.7`** ⇒
  "真机上到底哪套生效"**未实测**，要一条**未脱敏**的同接口抓包才能核。
- ⚠ 这一条**会往用户云盘写文件**（`uploadToCloud:true`，响应给 `fileId`）⇒ 接线时必须进
  `internal/exec/artifacts.go` 那本账，"清理"用的是**该账号自己的**凭据。

## 6. 已知"零样本"清单（本层**刻意不解释**的格子）

以及 path 上那个 `step` 段与 body 的 `key` 是否必须同字；① `totalLotteryCount` 是"累计"还是"剩余"

⚠ **上面那句"非成功码全部零样本"今天有一处例外，而且例外是代码不是证据**：
`newyear/*` 的 `90001` 在 `playAINewyearPayload` 里被**单独分类**成"会话过期"（其余非零码仍一律
`BadRequest` + 原文）。立这一支的依据**不来自本归档**，而是签到族那条实测
（`app-signin-samples.txt`：`90001` = `jwttoken` 没带上或已过期）—— 因为 app 层"刷一次票、重放一次"
那条自救支路只认这个变体，不分类就等于自救代码在这条链上永远不触发。
⇒ **本族会不会回这一码、回了以后刷票认不认，两个都仍无样本**（`docs/pending-decisions.md` **R11**，
补法：真跑一次只读链，中途让票过期）。
