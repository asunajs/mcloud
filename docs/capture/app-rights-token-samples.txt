### ⚠⚠ 更正（2026-09-20）：带 `hcy-cool-flag` 的体**是密文**，上一版写反了

上一版写的是"四个接口都带 `hcy-cool-flag: 1`，但**请求体与响应体全是明文**" —— **错**。
错因不是算法，是**取证面**：把 **App 日志**当成了线上形态。
App 日志记的是**加密前的请求 / 解密后的响应**（这正是它比代理抓包强的地方，
也正是它的陷阱 —— 看到明文不等于线上是明文）。

**两条独立证据**：

| 证据 | 事实 |
|---|---|
| 同一条 `user/getUser`，两个来源 | App 日志的体是明文 `{"userDomainId":…}`；代理抓包的线上体是 base64 密文。**同端点两处形态不同，因为一个是"日志"、一个是"线"** |
| 旧项目 `mcloud-sign/har/` 里 **396 条**带 flag 的实拍 | 逐条解开、**零例外**；请求与响应**双向**都是密文 |

⇒ 这个头声明的是"**我这个请求体已加密**"，而且**响应也按同一格式加密**（双向）。
**本文件 §2–§8 里贴的所有"请求体 / 响应"都是 App 日志里的逻辑明文，不是线上字节。**
要发真实请求（或要逐字节对齐抓包）就得按 §1.1 的信封加密。

> `queryRights` 与权益两个接口还额外带 `hcy-ios-option-enc: 1`；
> 实测这个头**不触发**任何加解密（见 `docs/capture/app-sms-login-samples.txt` §1.2 (d) 用例 C）。

### §1.1 整包信封（真钥匙：**AES-192**，2026-09-20 定案）

```text
body = base64( IV(16 字节，二进制) ‖ AES-192-CBC/PKCS7(
                 key = "2olBaQGYnEKoStYomsd1n7ax",     ← 24 字节
                 iv  = IV,
                 plain = 明文的 UTF-8 字节 ) )
响应：同一个格式（双向）。
```

| 项 | 值 |
|---|---|
| 钥匙 | `2olBaQGYnEKoStYomsd1n7ax`（**24 字节 → AES-192**，不是 AES-128）—— **原生**那一层 |
| 出处 | 旧项目 `packages/core/src/utils/encrypt.ts:3` 的 `REFRESH_TOKEN_KEY` |
| ⚠ 关键线索 | 该文件导出的 `aesDecryptWithDynamicIV` **全仓无人调用** —— 旧项目只用它**加密** note 的 refreshToken 体，从没用它解过码。钥匙一直在仓库里，只是没人把它和这个头连起来 |
| 命中面 | **396 条**实拍（跨 10 个 HAR、30+ 个 URL×方向），含 `querySpecTokenV2` / `queryAvailableBenefit` / `queryUserBenefits` / `getUser` / `avatar/get` / `refreshToken` / `queryUserMemberCards` … |
| 与 §8 的关系 | §8 那把 `uDjGSA8auFlbwDkY`（AES-128）**在同一批 396 条上 0 命中** ⇒ **至少两把钥匙、按链路分**：发码链路用 128 那把（有活体探针佐证），其余用这把 192 的 |

黄金向量：`test/golden/app-business-crypto-vectors.json` 的 `hcyCoolFlagBodyEnvelope192`
（5 条**实拍**，请求与响应两个方向都有，明文里无标识故可直接入库）；
Rust 消费者在 `crates/mcloud-core/src/crypto/tests/app.rs`。

### 1.2 ⚠⚠ 同日再更正：**第三把钥匙 —— H5 / WebView 那一层**（AES-256）

§1.1 收尾时写的"`user/getUser` 的体是 `base64(IV(16 个可打印 ASCII) ‖ CT)`，
形态像 `encodeData` 但 clientKey 也开不了" —— **已解开**。
原因不在钥匙，在**调用方**：那条 `getUser` 是 **WebView** 发的，不是原生。

| 项 | 值 |
|---|---|
| 钥匙 | `h7DLzCTAjn+altjy2a9E9FSt7AC6pmx1`（**32 字节 → AES-256**）|
| 格式 | 与原生**完全同形**（`base64(IV(16) ‖ AES-CBC/PKCS7(key, IV, 明文))`），双向 |
| 出处 | iOS App 沙盒的 **H5 离线包**：`Data/Documents/AIOfflinePKG/stable/ai-helper/assets/index-af02d869.js` 的 `Kr.coolFlagPivotal` |
| 调用点 | `AES_CBCDecrypt({ data, key: coolFlagPivotal, getIVFromEncrypt: true })` |
| 四组交叉对照 | WebView×256 = **3/3** ；原生×256 = 0/2 ；WebView×192 = 0/3 ；原生×192 = **3/3** |
| 覆盖面 | 14 条"可打印 IV"候选里 11 条命中（3 个接口）|

**判据（一句话）：三把钥匙是「谁发的」的函数，不是版本号。**
`x-yun-uni` + `x-yun-api-version` = 原生；`origin: mcloudlocal://` + `sec-fetch-*` = WebView。
**请求侧**还能看 IV：H5 用 `Bn.generateRandomString(16)`（随机**字符** ⇒ 全可打印），
原生用随机**字节**。⚠ **响应侧两族都是二进制 IV**（服务端生成），不能靠 IV 区分。

完整推导、H5 源码原文与踩坑记录见 `docs/upstream-app-business-api.md` §8.1。
黄金向量 `hcyCoolFlagWebViewEnvelope256`；Rust 测试三条 `app_cool_flag_*`。

⚠ **仍未解开**：`ILog`（它的体同样是"可打印 IV"，但**不属于**这把钥匙）；
`queryRights` / `IControl` / `thirdlogin` / `getSmsCode` 也各有解不开的条目。
**在拿到证据之前，不要把这几种信封互相套用。**

### ⚠⚠ 同一个能力有**两个**接口：原生走 V1，WebView 走 V2

**这条差点被我记错，所以单独写一节。**

在 App 日志里 `grep queryAvailableBenefitV2` 会得到 66 处 —— 但那**不是原生调用**。
按 `API Name:` 行统计，原生栈实际只调这两个：

| API Name（原生，`FXHttpBaseAccessor` 的 `API Response` 块） | 次数 |
|---|---|
| `https://ypqy.mcloud.139.com/isbo2/openApi/queryAvailableBenefit`（**V1**） | 14 |
| `https://ypqy.mcloud.139.com/isbo2/openApi/queryUserBenefits` | 10 |

那 66 处 V2 全部出现在 **WebView 的 JS console 行**上：

```text
[MCBaseWebViewController.m:7156][-[MCBaseWebViewController userContentController:didReceiveScriptMessage:]]
  [iPhone_wkwebview_js_log][Info] logg…
```

⇒ **H5 页面自己发的是 `queryAvailableBenefitV2`**，而且请求体是**另一种形态**：

| 调用方 | 路径 | 请求体 |
|---|---|---|
| **原生 App** | `queryAvailableBenefit`（V1） | `{"account":{"accountType":"1","accountName":"19900000001","nationCode":"+86"}}` |
| **WebView / H5** | `queryAvailableBenefitV2` | `{"account":{"userDomainId":"1990000000000000001"}}` |
| 同上，查单个权益 | `queryAvailableBenefitV2` | `{"account":{"userDomainId":"1990000000000000001"},"benefitNo":"RHR135"}` |
| **WebView / H5** | `queryUserBenefits` | `{"account":{"userDomainId":"1990000000000000001"},"isNeedBenefit":0}` |
| **原生 App** | `queryUserBenefits` | `{"isNeedBenefit":1,"account":{"accountType":"1","accountName":"19900000001","nationCode":"+86"}}` |

判据是 HAR 的 `_application`（`docs/client-profiles.md` 的老办法）：这批 `ypqy` 条目
**8 条全部**是 `com.apple.WebKit.Networking`，**没有一条**是原生。

> **⇒ 这是"同一条接口在原生与 WebView 上不同"的第 3 个实例**
> （前两个：`querySpecTokenV2` 的 `toSourceId` / 设备头段数；`hcy-cool-flag` 的有无）。
> 但这次**连路径都不同**（V1 vs V2），不只是头和参数 —— 比前两个更难发现。

#### 顺带一条方法论坑：App 日志里"接口名"出现在**两种**地方

| 位置 | 含义 |
|---|---|
| `API Name:` + `*************Request Start***************` | **原生栈真的发了**这个请求 |
| `[iPhone_wkwebview_js_log]` 行里的 URL | **H5 页面自己发的**（App 只是把 JS console 转出来） |

**`grep <接口名> FXTrace*.log` 会把两者混在一起。** 判断"到底谁在调"必须按
`API Name:` 行统计，或看 HAR 的 `_application` —— 只看 grep 命中数会得出反的结论
（我这一轮就先得出了"原生也在调 V2"的错结论）。

### V2 的响应字段比 V1 **多**（同一个 `benefitNo` 的完整形态）

V1 的条目只有 `benefitNo` / `benefitValue` / 可选 `reserve3`；
**V2 带 `benefitNo` 查询时**返回的条目是这样的（实测，脱敏后逐字）：

```json
{"benefitNo":"RHR135","benefitValue":"500000",
 "benefitName":"aitokens","benefitDesc":"aitokens",
 "benefitIconUrl":"https://eos.guangzhou-2.cmecloud.cn/…/RHR135.png",
 "isCalExtreme":1,"strategy":2,
 "benefitStatus":"2","benefitUsed":"100000",
 "reserve1":"","reserve2":"","reserve3":"[50万 tokens/月]Token",
 "includeMemberBenefit":"0"}
```

三点：

1. **`benefitValue` 是总量、`benefitUsed` 是已用量** —— 两者都是**字符串**。
   算剩余量要自己减，且要处理 `"0"`。
2. **`reserve1` / `reserve2` / `reserve3` 在 V2 里都出现**（空的是 `""`），
   而 V1 里**只有非空的 `reserve3` 才出现**（§2 的坑 2）。
   ⇒ 同一份数据的两个视图，**键的存在性不同**，别用同一套解析。
3. `benefitStatus: "2"` / `strategy: 2` / `includeMemberBenefit: "0"` 的含义**未查，不猜**。

### ⚠ 这批响应走的是 **gzip + chunked**（不是应用层协议）

`ypqy.mcloud.139.com` 的响应头实测：

```text
Content-Type: application/json
Content-Encoding: gzip
Transfer-Encoding: chunked
Vary: Origin
```

⚠ **Reqable 导出的 HAR 里，有几条把 chunked 的原始帧留了下来**，看起来像
"base64 密文"，其实解出来是：

```text
140\r\n            ← 十六进制块长（0x140 = 320 字节）
<320 字节 gzip>    ← 1f 8b 08 …
\r\n
0\r\n\r\n          ← 结束
```

⇒ **这是 HTTP 层的分块，不是上游发明的编码。** 应用层就是普通 JSON。
用 `reqwest` 的话要**打开 `gzip` feature**（`reqwest = { features = ["gzip"] }`），
否则拿到的是压缩字节。

> 踩坑记录：我第一次看到 `MTQwDQofiwgAAAAA…` 这种响应，第一反应是
> "`hcy-cool-flag` 的密文"，差点写进文档。**判据是响应头，不是响应的长相** ——
> `Content-Encoding: gzip` + `Transfer-Encoding: chunked` 一票否决了那个猜想。

## 4. 换 token：`user/auth/refreshToken`

```http
POST https://user-njs.yun.139.com/user/auth/refreshToken
Content-Type: application/json;charset=UTF-8

{"userDomainId":"1990000000000000001","clientType":"412"}
```

响应：

```json
{"success":true,"code":"0000","message":"请求成功",
 "data":{"token":"SYNTH001|1|RCS|1792245335331|AAAA…A.AA…（201 字符，见下）",
         "expireTime":2592000}}
```

### ⚠⚠ 新的一条"跨端常量不许互搬"（`clientType`）

**App 发 `"412"`**，而旧 TS 项目里 `refreshToken(clientType = "414")`。

| 位置 | 值 | 来源 |
|---|---|---|
| App 的 `refreshToken` / `getSmsCode` | `"412"` | 实测（本文件 + `app-sms-login-samples.txt`） |
| 旧 TS 项目的 `refreshToken` 默认值 | `"414"` | `docs/business-feature-inventory.md` |

⇒ **414 不是 App 的码**。这类"同一个接口、同一个字段名、两端不同值"已经犯过两次
（`Authorization` 前缀、签名密钥、`version`、`toSourceId`），这是**第五处**。
拿码之前照旧先问："它出现在哪个端？由谁发出？"

### 另外三点

1. **`expireTime: 2592000` 是秒**（= 30 天），不是毫秒、不是绝对时间戳。
2. **`code` 是字符串 `"0000"`**，且**与 `success: true` 并列** —— 这个信封又是另一种
   （`success` + `code` + `message` + `data`）。见 `docs/capture/app-api-families.txt`。
3. **这条接口慢是常态**：实测一次 **28.4 秒**才返回 200，紧贴 30 秒超时线。
   别把"慢"当"挂了"。
4. 它比 A 族其余接口**多两个头**：
   - `x-yun-api-version: v1`
   - `x-UserAgent: 412|iPad|ios 26.6|12.6.0-200` ← **第 1 段是 `clientType`（`412`）**，
     不是 `iPad`。同一个头在别的接口上是 `iPad|iPad|ios …`。

### `token` 的精确形状（脱敏，等长）

```text
SYNTH001|1|RCS|1792245335331|AAAA…（201 字符）
 ↑8 段长 1   3    13 位毫秒      载荷 172 字符
```

| 项 | 值 |
|---|---|
| 总长 | **201** |
| 分段 | `|` 分隔 **5 段**，各段长 `[8, 1, 3, 13, 172]` |
| 第 1 段 | 8 字符混合大小写字母（合成值形如 `AbCdEfGh`） |
| 第 2 / 3 段 | 常量 `1` / `RCS` |
| 第 4 段 | 13 位毫秒时间戳 |
| 第 5 段（载荷） | 172 字符，含 `_` ×4、`.` ×1、`-` ×1；**位置固定**：`_` 在 24 / 71 / 82 / 129，`.` 在 29，`-` 在 171 |

⚠ **这个 `token` 与 `Authorization` 里的 `authToken` 不是同一个东西**（后者在整串里）。
两者的关系**未验证** —— 不要互换，也不要拿它去覆盖 `account_state.jwt_token`
（那条教训见 `docs/credential-boundary.md`）。

## 5. 待领取：`market/signin/page/pointsNotClaimed`（**语义未定案**）

```http
GET https://caiyun.feixin.10086.cn:7071/market/signin/page/pointsNotClaimed
（无请求体）

{"code":0,"msg":"success","result":true}
```

### 观测到的取值

同一账号 09-19 07:52–19:14 共 26 条：

| 时段 | `result` |
|---|---|
| 07:52:05 → **14:37:14** | `true`（9 条） |
| **14:38:54** → 19:14:05 | `false`（17 条） |

**一次干净的翻转，没有回摆。**

### 翻转窗口里 App 侧发生了什么（HAR 交叉，14:38:46–14:39:17）

```
14:38:46  打开签到页   m.mcloud.139.com/portal/mobilecloud/index.html?path=newsignin
14:38:49  H5 发一串调用 startSignIn / infoV3 / doTaskPost / taskListV3 / getPopInfo / popup
14:38:5x  ← 翻转发生在这里
14:39:17  再次 GET pointsNotClaimed → false
```

（该 HAR 里 `startSignIn` 的响应显示当天**已经签过**：`signCount=1`、
今日格 `{d:19, s:true, n:3, t:true}`。）

### ⇒ **不把翻转归因到某一条**（这是本节的重点）

窗口内有**至少四个候选动作**：打开签到页、`startSignIn`、`doTaskPost`、页面渲染。
单看这一次无法区分。两个都还站得住的读法：

| 读法 | 与什么吻合 | 与什么冲突 |
|---|---|---|
| (a) **"有没有现在就能领的"**（≈ 我们的 `toReceive > 0`） | 与我们 CLI 同日领掉那 6 豆后 `toReceive` 归零吻合 | 07:52 起就是 `true`，而当时是否已有可领项**未核实** |
| (b) **"今天还有没有未领取的签到积分"** | 与"打开/走完签到页后翻 false"吻合 | 14:38:49 那条 `startSignIn` 的响应显示**当天此前已签过**，那它不该是翻转原因 |

**判据（下次抓包时的最小实验）**：需要一个**只签到不领取**或**只领取不签到**的窗口 ——
即两个动作分开做、中间各取一次 `pointsNotClaimed`。目前的数据里两者总是一起发生。

### 消费者是谁（已确认）

App 日志显示它由 **`MCCreditStateAction`**（`FXHttpBaseAccessor sendRequest:`，
回调 `creditStateCallback:`）在**一个 WebView 控制器 `viewDidLoad` 之后**发出。
⇒ 用途像"签到入口的小红点 / 角标"，**不像**业务数据源。
别把它当成"可领取数量的权威来源" —— 数量仍然只能来自 `infoV3.receiveList`。

### 一个奇怪的头

这个接口的 `Content-Type: text/xml;charset=UTF-8`，但**返回的是 JSON**。
照抄即可，别"修正"成 `application/json`。

## 6. 同窗口里签到族的其余 H5 调用（**`result` 有五种形态**）

同一 HAR（14:38:49）里，签到页还发了这些：

| 接口 | 请求体 | 响应 |
|---|---|---|
| `popup` | 无 | `{"code":0,"msg":"success","result":false}` |
| `getPopInfo` | `{"clientType":"iphone","version":"12.6.0"}` | `{"code":0,"msg":"success","result":{"showPop":false}}` |
| `doTaskPost` | `{"client":"app","deviceId":"<smid>"}` | `{"code":0,"msg":"success"}` ← **没有 `result`** |
| `taskListV3` | `{"marketname":"sign_in_3","client":1,"clientVersion":"12.6.0"}` | `{"code":0,"msg":"success","result":[ … ]}` |
| `getCode` | 无 | `{"code":0,"msg":"success","result":"<base64，56 字符>"}` |

### ⚠ `doTaskPost` 的 `deviceId` —— 与我们的 `smid.rs` **逐字对拍成功**

```json
{"client":"app","deviceId":"BAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=="}
```

（上为**等长合成值**：`B` + 86 字符 + `==`，共 89 字符；真实值不落库。）

这个值就是 `'B' + base64(smid)` 那个 `deviceId`（见 `docs/capture/app-signin-samples.txt` §4）。
三点值得记：

1. **在 JSON 体里不转义**：`/` 与 `+` 原样出现；在 query string 里则转义成
   `%2F` / `%2B`（见同 HAR 的 `startSignIn?deviceId=…`）。**同一个值两种编码，别混用。**
2. **末尾是两个 `=`**（规范只需 1 个）—— 与既有记录一致，**原样透传**。
3. 这是该实现的**第一个第三方对照物**：此前只有"我们自己的产出"和"HAR 里的真值"，
   现在多了一条"上游页面自己在用同一个值"。

### `taskListV3` 的条目形状

```json
{"id":549,"marketname":"sign_in_3","groupid":"time","enable":1,
 "name":"开启备份领好礼","description":"开启备份，云端无损存储",
 "icon":"https://img.mcloud.139.com//uop_prod/20260910/….png","steps":[],
 "starttime":"2026-09-10T16:00:00.000+00:00","endtime":"…"}
```

⚠ `starttime` / `endtime` 是 **ISO 8601 带 `+00:00` 偏移**的字符串
（与 §3 的 `yyyyMMddHHmmss` 是**两种完全不同的时间格式**，都在同一端）。
`steps` 是数组，实测为空。`icon` URL 里有**双斜杠** `…139.com//uop_prod/…` —— 原样透传。

### ⚠⚠ 别写"读 `result` 就知道成败"的通用解析器

把 §2–§6 出现的 `result` 放在一起看，它至少有**五种**形态：

| 接口 | `result` |
|---|---|
| `popup` / `pointsNotClaimed` | 布尔 |
| `doTaskPost` | **整个键不存在** |
| `getPopInfo` | 对象 `{showPop}` |
| `taskListV3` | 数组 |
| `infoV3` / `startSignIn`（见姊妹文档） | 大对象 |

再加上 `code` 的语义也相反（埋点用 `1` 表示成功）—— 与
`docs/capture/app-api-families.txt` 的结论一致，**逐接口解析**。
