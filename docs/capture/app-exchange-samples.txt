## 1. 静态证据（H5 源码逐字）

### 1.1 三条接口的定义

出处 `har/h5-signin/newsignin.336f18c3.js`（压缩单行，位置 182436 / 182762 / 283951）。
两个模块各有一份相同的定义（读一个模块会漏，见 `app-signin-samples.txt` §7）：

```javascript
getPrizelistData: function (e) {
  return c["a"].get("/ycloud/signin/page/exchangeList",
    {params: e, headers: {showLoading: t, "content-Type": "application/json"}})
},
exchangePrize: function (e) {
  return c["a"].post("/ycloud/signin/page/exchangeV3", JSON.stringify(e),
    {headers: {showLoading: !0, isDeviceId: !0, "Content-Type": "application/json;charset=UTF-8"}})
},
getSlidePuzzle: function (e) {
  return c["a"].post("/ycloud/auth-service/slide/getSlide", e, {headers: {showLoading: !0}})
}
```

⇒ **列表是 GET + query，下单是 POST + JSON body**，且下单标了 `isDeviceId: !0`。
`Content-Type` 是 `application/json;charset=UTF-8`（带 charset，与列表那条不带的不同）。

### 1.2 兑换请求体（调用点逐字）

两个组件（云盘版位置 213735、139 邮箱版位置 257342）各有一处，形状一致：

```javascript
n = {
  prizeId: U.value.prizeId,
  client: D.value ? "mini" : B.value ? "app" : "out",
  clientVersion: Object(d["c"])(),
  puzzleOffset: t,
  smsCode: ""
}
i["a"].exchangePrize(n)
```

⚠ **`client` 一共四种取值**，不是一个布尔：
`mini`（小程序）/ `app`（App）/ `out`（H5 外嵌）/ `email`（139 邮箱版组件里 `D.value?"email":"out"`）。
我们是 **App 端** ⇒ 预期实拍是 `client: "app"`。抓包时要确认它真的是 `app`，
而不是照抄参考项目。

- `puzzleOffset: t` —— `t` 是滑块结果（§1.4）。**H5 恒传**，不走"没有滑块就不传"的分支。
- `smsCode: ""` —— H5 **恒传空串**。参考项目的 `exchangeV2` 也带这个参数。
  它什么时候非空，目前**无证据**（见 §6 待验证问题 3）。

⭐ **判据：`614` 与 `615` 在 H5 里共用同一句文案** —— 而 `app-signin-samples.txt` §4.2 的

`e.data.msg || "验证失败"` —— 服务端给的文案，不在客户端那张表里。

⭐⚠ **上面这张表只是「H5 客户端认识的那一档」，不是上游码的全集。**
实测在它之外还遇到三个，**一个都不许往表里硬塞**：

| 码 | `msg` | 何时 | 出处 |
| --- | --- | --- | --- |
| `501` | `滑块验证参数不能为空` | `puzzleOffset` 空串 / `null` | §6 第 1 条 |
| `415` | `奖品单日已耗尽` | 奖品的当日份额用完 | §5.5 ② |

⚠⚠ 尤其 **`2301` 是四位**，而表内表外其余码（`407/415/420/421/501/514/610/614/615`）
全是三位 ⇒ **别按"码都是三位"的形状去写解析、也别按形状去猜**。
⚠ 而 `415` 的 `msg`（`奖品单日已耗尽`）**与 `420` 的**（`该奖品每日限兑，您今日份额已用完`）
说的是**两层不同的事**：前者是**奖品的池子**空了，后者是**我自己的份额**用完了 —— 别混。

> ⭐ **2026-09-22 第五轮补记（§5.6）**：`420` / `421` 这两个码**至今一次都没露面**，
> 但本轮从 `exchangeList` 的**字段侧**找到了它们看起来的对应物 ——
> `limit` 的 `1` = "明日再来"（↔ `420` 的文案"您今日份额已用完"）、
> `4` = "您已兑换过此类奖品"（↔ `421` 的文案"您本月份额已用完"），
> 而 `4` 的**字段依据**是 `monthGroupLimit`（数组）+ `limitMonthQuantity`。
> ⚠ 这**只是假设**（两边文案同向、字段自洽），**不能当结论** ——
> 服务端究竟还回不回 `420`/`421`（还是像 `415`/`2301` 那样另有一套码），**没有样本**。
> ⚠ 顺带：`limit == 1` 的样本本轮**一件都没有**（四件是 `2`/`4`/`4`/`4`），
> 那个取值目前只有 §5.1 的文案字典在支撑。

> "上游换了编码"变成"默默少解尾部几个字节"，而解算器在残缺图上照样会吐一个很像答案的数。
> 落点：`internal/upstream/app_exchange_slide.go`，反向用例
> `TestParseSlidePuzzleRejectsUnpaddedBase64`。

**`puzzleOffset` = 拼图块左边缘在底图（680×400 像素坐标）里的 x。**
可滑范围 `x ∈ [0, 680-96] = [0, 584]`。

| 记录 | 量出的块左缘 | 提交的 `puzzleOffset` | 偏差 | 上游回 |
| --- | --- | --- | --- | --- |
| 12992 | **320** | 261 | 59 | `514` |
| 13027 | **146** | 99 | 47 | `514` |
| 13054 | **197** | 373 | 176 | `514` |
| 13065 | **140** | **144** | **4** | **`code 0`** |

两个探针（`cmd/exchange-probe measure-slide`，纯离线、只吃两张 PNG）：

1. **仿射残差**：对每个候选 x 拟合 `底图 ≈ a·拼图 + b`，取 `1-R²` 最小者。
   位置对时 `底图 = k·拼图` 精确成立 ⇒ `1-R² ≈ 0`（实测 0.07~0.34）；
2. **列亮度差**：缺口是把原图**压暗**出来的 ⇒ 按列取"块所在高度带"与"紧邻上方参考带"
   的均值差，取半深度穿越点作左缘。

⇒ 两者在 4 张图上**逐张一致**（320 / 146 / 197 / 140）。

⭐⭐ **服务端对 `puzzleOffset` 的容忍度：落在 `[4, 41)` 像素区间。**

- **下界 4**：13065 的题面量出 `140`、提交 `144`（差 4）⇒ **通过**。
- **上界 41**：三条 `514` 的偏差分别是 59 / 47 / 176。
  ⚠ 但"哪条题面对哪次提交"是**按记录顺序配的**（`getSlide` 紧邻其后 2~4 秒的那条 `exchangeV3`），
  属于推断。**按最有利的配对重算**（拿最接近的题面去配每一次提交），
  三次偏差的最小值是 `|99 − 140| = 41` ⇒ 即使配对全错，失败的偏差也 **≥ 41**。
  ⇒ 容忍度只能夹到 `[4, 41)`。
  ⭐ 而**成功那条自己就把配对钉住了**：四张题面里只有 13065 那张（`140`）与 `144` 差 4 像素，
  另外三张分别差 121 / 53 / 115 —— 若配错，那笔就不该成功。**结果反证了配对。**

⚠ **别把上界写成"±5"**：本次只有 4 条样本，只能夹到 `[4, 41)`；容忍度究竟是多少、
是否随图变化，**仍无实证**。同理，`140` 与 `144` 这 4 像素的差是"探针系统偏差"
还是"服务端容忍"，本次样本**分不开**。

⚠ **一个会让人白跑一趟的坑**：探针①最初用的是"比值 `底图/拼图` 的变异系数最小"，
在**平滑背景**（天空）上**退化了** —— 天空没纹理时比值的不确定性全由分母决定，
cv 与 x 无关（实测全域极差只有 `0.00003`，等于没测，却照样打印出一个"最优 x=0"）。
⇒ 判据在**特定输入**上退化时**不会报错，只会给一个看起来很像答案的错答案**。
凡"取极值"的判据，都要顺手打一句**"最优与次优差多少"**当自检。

⭐⭐ **原项目已经有一份本地算法，量纲与本实测独立吻合**（2026-09-22 核）：

`packages/shared/src/slide/match.ts` 的 `matchSlide(bg, puzzle, …)` 三步：
① 对底图做 **Sobel 边缘检测**（整数近似，用 `|gx| + |gy|` 代替 `sqrt`）→ 边缘强度图；
② 从拼图里取**轮廓像素**（`alpha > 128` 且四邻域存在透明像素的点）；
③ 对每个候选 `offset`，把轮廓点平移过去、累加底图边缘强度，取**和最大**者；
另附一个 `confidence = bestScore / avgScore`。

- ⭐ **它的搜索范围就是 `[0, bgW - pzW] = [0, 584]`** —— 与上面那条量纲**独立吻合**
  （它把 `offsetX` 直接当 `puzzleOffset` 用：`task.ts:93` 算 → `:137` 发）。
- ⚠ 它的 `puzzleOffset` 默认值是 **`0`**：取题失败时打一句"使用默认偏移量 0"
  **照常下单**（`task.ts:91-96`）。见 §6.1 线索 1。

⭐⭐ **三算法对拍（2026-09-22 补做）：三个独立口径差 1 像素。**

题面图此前丢过一次（§7 第 3 步的教训），本轮**从 Reqable 的响应缓存里捞回来了**：
`~/Library/Application Support/com.reqable.macosx/tmp/10c86a8d-2eef-404d-a6d9-63b6f3367c0c`
（293926 字节）就是那条 `getSlide` 的响应体 —— `picWidth 680` / `picHeight 400` /
`puzzleWidth 96` / `picType png` / `puzzleLeft null`，与上面 §5.3 那段逐字一致。
解出 `picture.png`（680×400，8-bit colormap）+ `puzzle.png`（96×400，RGBA）。
⚠ **它是哪一条**：缓存文件本身**不带记录号**，按**量出值当指纹**反推 ——
本张量出 `320`，而上表四条的量出值是 `320 / 146 / 197 / 140`，只有 **12992** 那条是 `320`
⇒ 判定为**记录 12992** 那条题面（是推断，不是读到了 ID）。

对拍跑的是**原仓库那份 `match.ts` 逐字未改**（`calcPuzzleOffset`，用原仓库自己的 `tsx`
与它自己的 `fast-png` 解码器；拷贝件 sha256 `61573aff…` 与原文件一致，`diff` 只有
"删 import + 内联类型 + 加诊断"三类纯新增）—— **不是转写版**，免得把转录错误混进核对：

| 算法 | 口径 | 结果 |
| --- | --- | --- |
| 原项目 `matchSlide` | 轮廓点 × 底图边缘响应**和最大** | **321** |
| 本仓库探针① | 仿射残差 `1-R²` **最小** | **320** |
| 本仓库探针② | 列亮度差**半深度穿越点** | **320** |

⇒ **三个口径不同、互相独立的度量，一致到 1 像素。** 上一版那句"只能说量纲口径一致、
不能说值一定相同"**现在有答案了：值相差 1px**（不是 0，也不是"很大"）。
原版得分前 5 名：`321`(41699) > `322`(33011) > `319`(32069) > `320`(31912) > `323`(31506)
—— 前四名挤在 319~322 这 4 个像素里，说明**它的度量本身分辨率就在 1~2px 量级**。

⚠ **那 1px 的归属未定，但已排除一个嫌疑。** 原版轮廓循环是
`for (y = 1; y < pzH-1; y++) for (x = 1; x < pzW-1; x++)`，**结构上看不到拼图最左一列**
（实测 `x=0` 这列有 94 个不透明像素）。曾疑心这是"约定差"（量不到左沿 ⇒ offset 系统性偏大 1），
于是做了**判决性实验**：给拼图左边补一列透明（96→97 宽，不透明区 `x∈[0,94]` → `x∈[1,95]`）。
结果 —— 轮廓点 `310 → 404`（**+94**，正好是 `x=0` 那列的不透明像素数），
而 offset 只随坐标平移（`321 → 320`），**拼图落点始终是 `bg-x 321`，纹丝不动**。
更反证的是：补进左沿后，321 那个点的得分从 `41699` **涨到 `48811`** ⇒ 左沿信号是
**加强**了这个峰，不是把它拉向 320。
⇒ **假设被否掉**：原版的 321 不是循环边界的 bug，是它的度量**确实**把落点定在 321。
1px 到底该记 320 还是 321，**本次单张题面判不了** —— 三者量的不是同一条边
（原版量"轮廓与背景边缘的吻合"，探针②量"缺口左边界在哪"，探针①量"整块拟合残差"）。

**完全吞掉** ⇒ **别为这 1px 去改算法**，该做的是提交前**主动加 4~40px 的抖**。

⚠ 顺带一条**反面教材**：核对之前，"三算法一致"这句话在本文件里**写了两版**——

#### 5.3.1 ⭐⭐ 2026-09-22 第三轮：解算器在 Go 侧落地，并在真机上**过了滑块那一关**

> ⚠⚠ **先纠正本节上面一条建议**：上面写"该做的是提交前**主动加 4~40px 的抖**"——
> **那是错的**，本轮实测把它否掉了（见下面的"容忍度"）。**不要加抖，直接提交算出来的值。**

**① 第二口径换成「原项目 `matchSlide` 的忠实移植」。**

原本想用本节记的探针②（列亮度差**半深度穿越点**）当第二口径，**在真实题面上连栽两次**：

| 题面 | 探针②给出的"带宽" | 应为 | 错在哪 |
| --- | --- | --- | --- |
| 14:56:11 那张 | `111` | 95~96 | 左沿被拖左 15px |
| 14:57:36 那张 | `37` | 95~96 | 找到的根本不是缺口 |

根因三条，**都是"假设不成立"，不是实现写错**：

1. ⚠⚠ **剖面基线不是 0** —— 参考带（块上方 40 行）与块所在带之间有**系统性亮度差**
   （背景垂直渐变）：实时题面上带外基线约 `50`，而缺口深度只有约 `46`。
   按"从 0 起算的半深度"取阈值 ⇒ 阈值落到基线**下方** ⇒ 左沿被一路拖进基线。
2. ⚠ **不该去猜宽度** —— 缺口宽度**就是**拼图块的宽度，是**已知量**
   （块包围盒宽 95、`puzzleWidth` 报 96）。让算法从剖面自己"找边界"等于把已知信息扔掉。
3. ⚠ 更根本的：这个口径假设"**缺口是唯一的亮度差来源**"。真实背景有水平结构时就不成立。

⇒ 第二口径换成**原项目 `matchSlide` 的逐字移植**（Sobel 边缘 × 拼图轮廓）——
它是**边缘**度量，不依赖亮度均匀假设。⭐ 而且**可证忠实**：在上一张证据图上
**逐字复现**了原版的得分（这张表就是"移植有没有走样"的判据）：

| | offset | 得分前 5 |
| --- | --- | --- |
| 原版（TS，原仓库自己的 `fast-png`） | **321** | `41699 / 33011 / 32069 / 31912 / 31506` |
| Go 移植版 | **321** | `41699 / 33011 / 32069 / 31912 / 31506` |

轮廓点数也同为 **310**。⚠ 复现它的关键是**三个容易"顺手改好"的细节**，一个都不能动：
- 灰度是**整数近似** `(r*77 + g*150 + b*29) >> 8`（不是浮点 `0.299/0.587/0.114`）；
- 边缘强度有 **`>> 2` 与 `min(255, …)`**（省了得分大 2.6 倍、名次也会变）；
- 匹配循环**只判上界** `if (bx < bgW)`，**不跳左边界列**（就是 §5.3 上面讨论过的那一列）。

⭐⭐ **还有一个更隐蔽的**：底图是 **colormap PNG**，而原版对它的口径**不是**"展开成 RGB" ——
`fast-png` 对调色板图报 `channels: 1`、`palette: true`，`data` 是**调色板索引**
（实测 `680×400 ⇒ dataLen 272000`，即一字节一像素），而原版 `base64ToImageData` 的
`channels === 1` 分支**直接把索引当灰度**用了 ⇒ **它的 Sobel 是在索引图上做的**。
⚠ 这看着像原版的一个 bug（索引不携带亮度），但**照抄它**才复现得出上面那张表。
不照抄的实测后果：得分 `27400 / 20988 / …`、答案 `319` —— 值只差 1~2px，**但对拍就失效了**
（对不上任何已记录的数字）。⇒ ⭐ **"看着像 bug"不是跳过它的理由；"能不能复现基准"才是判据。**
⭐ 这张表的**可复跑底本**在 `target/slide-evidence/README.md`（含原版 TS 与 Go 侧两条重跑命令、
溯源、以及"为什么不入库"）—— 该 README 里那条 `[4, 41)` 的旧建议**已于 2026-09-22 就地更正**
（见下面 ③），免得下一个人只读它、不读本文。

⇒ 两条**互相独立**的路子（它的线上经验 / 我们的真机实测）**对得上**。
⚠ 但它是为**规避风控**而抖、**不是**容错机制 —— 我们 `0` 偏差直接过，**没有理由抖**。
逐条对照见 [`../caiyun-go-exchange-and-runtime.md`](../caiyun-go-exchange-and-runtime.md) §3.9 第 4 行。

⚠ **四个落地要点（下次重写时别再踩）**：
- 请求体用字符串拼 + `core.Body([]byte(...))`，**不能**用 `WithJSONBody(map[string]any)` ——
  后者会按**字母序**重排键，与实拍键序
  （`prizeId → client → clientVersion → puzzleOffset → smsCode → deviceId`）不符。
- 实拍里另有两个头要自己补：`isdeviceid: true` 与 `origin: https://m.mcloud.139.com`
  —— `WithH5Headers` 不管这两个。
- ⚠⚠ **响应里的数字是 `json.Number`，不是 `float64`**（仓库 `core.ParseJSON` 开了
  `UseNumber` 保 19 位标识）。按 `float64` 断言**不报错、只是每个字段都静默变 0** ——
  本轮先撞了一次"清单全是 0"。`prizeId` 同理是**数字**，按 string 断言会拿到空串。
- `getSlide` 的 `content-type` 实拍是 `application/x-www-form-urlencoded;charset=UTF-8`，
  而 `WithH5Headers` 会补成 `application/json;charset=UTF-8` —— ⚠ **这条差异已知且能通**
