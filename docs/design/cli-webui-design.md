# CLI 与 WebUI 设计（重新设计）

> 本文是**重新设计**，不是对 mcloud 的移植。
> 参考 mcloud 的目的是**避开它踩过的坑**，而不是复刻它的形态。

---

## 0. 一句话

**WebUI 为主，CLI 只管「无头也能跑」的那几件事。**

判断标准只有一条：

> 这件事**需要人看着**吗？
>
> - 需要 ⇒ WebUI（扫码、填验证码、看日志、抢兑）
> - 不需要 ⇒ CLI（定时触发、刷新凭据、跑一条配好的链）

mcloud 的 CLI 有 **40+ 个子命令**（`login qr/sms/smid show/reset/refresh`、
`user init/list`、`migrate`、`fixture extract`、`live-room`、`capabilities`、
`auth refresh`、`signin` 一族带十几个 flag…）。本项目**不要那么多**：
多数子命令是"开发期工具"或"WebUI 能做的事在终端又做了一遍"，
而重复入口的代价是**两处都要改**。

---

## 1. CLI：只留"无头也能跑"的几条

**条数以 `crates/mcloud-server/src/cli/run.rs` 的顶层分派为准，别背数** —— 现算
（8 空格缩进那层就是顶层）：`grep -n '^        Some("' crates/mcloud-server/src/cli/run.rs`。
今天的长相是 5 条核心 + 2 条只读：

```
mcloud login    qr | sms <手机号> | app <手机号> | password | device   登录账号（交互）
mcloud run      <任务名> <账号>            跑一次任务
mcloud cron     <定时id>                  跑一条定时（供外部 crontab 调用）
mcloud auth     refresh <账号|--all>      刷新 auth 凭据
mcloud pipeline run <编排id>              跑一条编排
```

> `login app` 与 `login sms` **并列而不是合并**：App 端走另一套密钥、
> 另一套设备头，请求体还要 AES 加密 + 末 10 位错位，落盘的 `auth`
> 前缀也不同（`mobile` vs `pc`）。做成 `sms --app` 会让"我登的是哪一端"
> 在命令行上不可见，而端一旦搞错，产物是**错的身份** —— 之后每个任务
> 请求都会带着它发出去。

外加两条只读的：

```
mcloud tasks                              列出可用任务
mcloud pending                            查看本进程里还没清理的网盘产物
```

### 为什么是这几条

| 命令 | 为什么 CLI 需要它 |
|---|---|
| `login` | 扫码/短信**必须在没有 WebUI 时也能做**（首次部署、服务器上） |
| `run` | 排障：某条任务单独跑一次看输出，不必开浏览器 |
| `cron` | **外部 crontab 的入口**。见下 |
| `auth refresh` | 凭据将过期时批量续期，脚本里最常调的一个 |
| `pipeline` | 一条链手工重跑（WebUI 挂了或想看清退出码） |
| `tasks` / `pending` | 只读、无副作用：列任务清单、看本进程还没清的网盘产物 |

### `cron` 的语义：**外部触发，CLI 不常驻**

```
# crontab
0 8 * * *  /usr/local/bin/mcloud cron daily-sign >> /var/log/mcloud.log 2>&1
```

- CLI **不**跑调度循环、**不**长驻。时间由系统 crontab 管。
- `cron <id>` 只做一件事：按 `schedules.json` 里那条配置跑一次，然后退出。
- 退出码：成功 `0`、任务失败 `1`、**配置错误 `2`**。

**为什么不让 CLI 常驻调度**：常驻就意味着要处理"进程挂了""两个实例同时跑"
"重启后补不补错过的点"—— 而这三件事在 mcloud 的 server 里已经有完整答案
（水位线、错过策略、并发闸）。CLI 再实现一份就是**两处语义**，
而它们的表现差异极难发现（一个补跑、一个不补）。

> ⚠️ **两者不要同时跑同一条定时。** 水位线是"读→判→写"，不是跨进程的原子认领。
> server 在跑调度时，外部 crontab **不应**再触发同一条。这一点在
> `cron` 的启动日志里明确打印警告。

### **不做**的事（刻意）

| 不做 | 理由 |
|---|---|
| `schedules add/rm` | 定时是"配置"，**改配置文件或 WebUI**。CLI 里再做一个 CRUD 是第三个入口 |
| `pipelines add/rm` | 同上 |
| `user init/list` | 单用户工具，不需要用户管理子命令 |
| `migrate` | 没有旧库要迁移 |
| `fixture extract` | 开发期工具，不该进用户 CLI |
| `login smid show/reset` | 设备指纹是内部状态，用户改它只会搞坏账号 |
| 十几个 `--flag` | 参数走**任务自己的配置**，见 §3 |

**"不需要支持编排"** 按你的原话落地成：CLI **没有** `pipeline create/edit` ——
只有 `pipeline run <id>` 跑已有的。编排的增删改在 WebUI 或直接改
`data/pipelines.json`。

## 2. WebUI：登录闸 + 6 个页面

### 2.1 登录闸（跟随 mcloud）

第一道门是 **WebUI 自己的用户名/口令**，与"账号登录"是两件事：

| | 谁的凭证 | 存哪 | 谁用 |
|---|---|---|---|
| **WebUI 登录闸** | 你设的一个用户名/口令 | `users` 表（`sha256$` + argon2id PHC 串） | 浏览器 |
| **账号登录** | 移动云盘的 auth | `accounts.json` | 任务运行时 |

- 首次访问 ⇒ `/api/setup` 引导建管理员。**建之前其他接口一律 503**。
- **口令哈希两次**（用户口径，2026-10-01）：
  1. **浏览器先做一次** `SHA-256(明文)` 的小写 hex（`web/src/ui/password.ts`）；
  2. 服务端再对它做 **argon2id**（`m=19456, t=2, p=1, out=32`）落库 ——
     与 mcloud 同参数，两边金标向量可以对拍。

  库里的形态是 `sha256$$argon2id$…`：`sha256$` 前缀即"这一层是对**前端摘要**做的"的档位标记
  （用前缀而不是加列：老数据天然没有它，"有没有前缀"本身就能判档，不必写迁移开关）。

  * 服务端**从不要求**前端做那一次：收到明文就现场补（`to_digest_credential`）——
    缓存里的旧 bundle 因此不会被锁在门外。
  * ⚠ 它挡的是"**明文进服务端**"（日志、内存、备份）与口令跨站复用；
    **挡不住重放** —— 服务端最终认的就是那个摘要。要防重放得走"服务端下发挑战值"，本轮没做。
  * ⚠ `crypto.subtle` 只在**安全上下文**存在（`https://` 或 localhost）。
    从 LAN 用 `http://192.168.x.x:3000` 打开时会退回**发明文**（服务端那条兼容路）——
    这是**有意的降级**：那条路上与改之前完全一样，而不是"登录失败"。
    想要全程"明文不出浏览器"，就给它配 HTTPS。
- **老实例自动升级**：2026-10-01 之前建的库是 `argon2(明文)` 这一档。
  `/api/setup` 会自述 `passwordScheme: "plain"` ⇒ 前端这次发**明文**（发摘要谁也验不过），
  服务端验过之后**当场**把记录换成 `sha256$argon2id(摘要)`，此后自述翻成 `"sha256"`。
  升级**可回滚**：store 每次落盘都留上一份 `users.bak`（实测：升级后 `users.bak` 仍是老档串）。
- 会话是**服务端 session**（不是 JWT）：`HttpOnly` + `SameSite=Strict` cookie，
  登出即失效。
- 实测（2026-10-01，真实实例）：升级前自述 `plain` → 明文登录 200 →
  自述翻 `sha256` → **摘要登录 200** → 再发明文仍 200（兼容口）→ 错口令 401；
  `data/users.json` 从 `$argon2id$…`(97) 变成 `sha256$$argon2id$…`(104)。

> **为什么本地工具也要这道闸**：服务器的监听地址是可配置的
> （`MCLOUD_ADDR`）。今天图省事跳过认证，明天有人 `0.0.0.0` 一开，
> 整个网盘权限就挂在公网上。这道闸是**唯一的**边界，不能靠"应该只监听本地"。

### 2.2 页面

| 页面 | 职责 | 优先级 |
|---|---|---|
| **登录/初始化** | 首次建管理员、登录、登出 | P0 |
| **账号** | 账号列表、**添加账号（弹窗：扫码/短信/手机端/账密/凭据）**、编辑（昵称/设备号/凭据）、移除 | P0 |
| **总览** | 调度器状态、今日运行 / 账号凭据 / 定时与编排 / 网盘遗留、最近运行（见 §2.2.1） | P0 |
| **任务** | 按**后端给的分组**分栏列出任务、选账号运行、实时日志；参数在**单独的配置页**（`/tasks/<任务名>/config`） | P1 |
| **定时** | 定时 CRUD、启停、下次执行时间 | P1 |
| **历史** | 运行历史 + 日志回看 | P1 |
| **设置** | 实例与运行概况、**账户安全**（改口令/口令下限/会话时长）、存储信息、重启服务、账号与推送入口 | P2 |

**设置页还缺的（后端没接口，不画空表单）**：并发上限、全局通知渠道。
（改口令 / 口令下限 / 会话时长 / 存储信息 / 重启在 2026-10-01 都补上了后端，见 §2.2.4。）

**编排页保留完整 CRUD。** 这一条我最初设计成"只读"，**是错的** ——
需求里明确写了 WebUI 要含「定时与编排 CRUD」。已按需求落地：

| | CLI | WebUI | 配置文件 |
|---|---|---|---|
| 定时 | 只能跑（`cron <id>`） | **完整 CRUD** | 可直接编辑 |
| 编排 | 只能跑（`pipeline run <id>`） | **完整 CRUD** | 可直接编辑 |

**收敛的方向是 CLI，不是 WebUI。** 我先前把"CLI 不做编排增删"错读成
"WebUI 也不做"，那会让编排彻底没有图形入口 —— 而需求说的是
"CLI 不需要支持编排，有需要直接改配置文件"，主语是 **CLI**。

判据回到 §0 那条：**这件事需要人看着吗？**
编排的创建要填步骤、选账号、设 `continue_on_error` —— 那需要看着，
所以它属于 WebUI。而 CLI 是无头场景，给它一堆 flag 才是重复入口。

### 2.2.1 总览页的形态（2026-09-30 重新设计）

一屏四段，从上到下回答四个问题：

| 段 | 回答什么 |
|---|---|
| **引擎条** | 定时调度在不在跑、当下有没有任务在跑、下一次自动运行是**哪一条**定时 |
| **四张指标卡** | 今日运行（成功 / 失败 / 跳过）、账号凭据（到期）、定时与编排、网盘遗留 |
| **最近的定时任务 + 今日AI豆**（并排 2:1） | 左边：接下来几条各**还有多久**跑、上次跑成什么样；右边：**每个账号**今天AI豆进出多少 |
| **最近运行** | 最近 **5 条** + 一个「查看全部」入口 |

**命名口径**：界面上写「AI豆」（现行叫法），不写「云朵」—— 后者只出现在
**引用上游接口名**的地方（`cloudRecordV2` 那条流水）。见 `docs/conventions.md` §5.5。

**记账口径（2026-09-30，需求方点出）**：AI豆**按账号各记一本账**，
**不做跨账号合计** —— 加出来的"总AI豆"哪个账号都用不了（豆不能跨账号花）。
所以那张卡是一个账号一行；哪天想"优化"成一个总数，先回来看这一句。

两条口径写在这里，免得下次又被"顺手加一格"：

- **指标卡那四格只用现有接口能拿到的数**（`/api/status`、`/api/runs`、
  `/api/schedules`、`/api/accounts`）—— 没有为它新增任何后端字段。
  派生规则（"今日"取本地 0 点、7 天内到期算"将到期"、谁的 `nextFireAt` 最小）
  全部在 `web/src/pages/dashboard-page.tsx` 里以纯函数形式给出，一眼可复核。
- **收敛到 5 条**：原先总览把 `/api/runs` 的全部记录（后端上限 100 条）铺成一张表，
  于是它成了第二个历史页，第一屏被表格顶下去 —— 而"一眼看清现状"正是这一页的
  全部意义。看全量细节是历史与日志页的事。

⚠ **「今日AI豆」那一格**：它**要一个专用端点**（`GET /api/beans/today`，由云朵记录汇总）。
端点**已落地**（`crates/mcloud-server/src/routes/beans.rs`，已由 `routes/mod.rs` merge）
—— 本节原先写"后端还没有这个端点、它显示「待接入」"，已过期。
口径与仍缺的收尾见 `docs/task-inventory.md` §5。

⚠ 另记一条**没做**的：数据**年龄**由页头的「更新于 22:31」承担，
这一页**不轮询** —— 自刷会让人以为那个时间戳在动，其实只是又采了一次样。

### 2.2.2 账号页的形态（2026-10-01 重构）

用户口径：「添加账号可以用新路由或者弹窗唤出而不是常驻」+「账号只有移除没有编辑」
+「通过添加 auth 创建新账号未实现」，要求仍是**简单、明了、功能全而言简意赅**。

| 区块 | 内容 |
|---|---|
| 页头 | **只有动作**：**添加账号**（按钮，打开弹窗）。标题与「刷新」都不在这里 —— 见下面那条 2026-10-03 的改动 |
| 账号列表 | 一行一个账号：昵称（回落掩码手机号）、设备号、凭据到期、平台徽章；右侧 **编辑** / **移除** |
| 添加账号（弹窗） | 客户端形态（Windows/macOS）+ 五条路：扫码 / 短信 / 手机端 / 账号密码 / **凭据** |
| 编辑账号（弹窗） | 昵称、设备号、**换凭据**（留空 = 不改；pc 凭据才出现形态选择） |
| 本机设备指纹 | 机器级（扫码的 `dID`），保留在页面底部 —— 它不是"某个账号"的属性 |

三点判断：

1. **弹窗而不是新路由**。导航项上限是硬约束（§2.1 那条：9 项是上限），
   而且"添加账号"是**在一个页面里完成的一件事**，不是一个新的目的地 ——
   新路由会多一个需要返回的页面，弹窗不需要。四条登录路径的表单本身
   300 多行，常驻会把"我有哪几个账号"压到第一屏之外，而那句话才是主语。
2. **凭据从不出现在界面上**。「编辑」里那格永远是空的输入框：服务端也从不回显它
   （列表 DTO 里没有 `auth`）。所以编辑是 **PATCH（给了才改）**，
   而不是像设置那样的"整体替换" —— 否则改个昵称也得重新粘一遍凭据。
3. **一个账号一份读数**这条同样适用（AI豆那张卡，见 §2.2.1）。

### 2.2.7 页头与外框：标题只在 navbar、「刷新」是 navbar 上的图标（2026-10-03）

两条用户口径，各自改掉一类"看着乱"：

**① 页面标题只出现一次。** 之前**八个页面**各自在页面顶部写了一遍 `<h1>`，
而外壳那个 sticky navbar 本来就在显示同一个 `navItem(id).title` ⇒ 每页顶部都是
同一句话挨着出现两遍（连 `text-base font-medium` 都一模一样）✗。
现在：**标题只由 navbar 显示**（它在滚动时还在；窄屏侧栏是抽屉，所以它是
"我在哪一页"的唯一指示 ✓），页面里那一行只剩动作（添加/新建…）。
⚠ 新增页面时**不要再写 `<h1>` 标题** —— `app.tsx` 那个 navbar 标题旁边写着这条。

**② 「刷新」搬成 navbar 上的图标**（用户口径：「刷新做成图标放上面可行吗」）。
九个页面 + 任务配置子页的页头刷新按钮都撤了，统一由 navbar 上那个环形箭头触发。

| 要点 | 做法 |
|---|---|
| 刷新的是**什么** | **当前页自己的 `load()`** —— 页面登记给外壳（`web/src/ui/page-refresh.ts`）。不是"重新挂载当前页"：那会把任务页正在看的日志、勾好的账号、编排页填了一半的表单、滚动位置全清掉 ✗ |
| 为什么不能用信号登记 | ⚠⚠ lite 是**同步刷新**的，而页面登记的时刻正是外壳在渲染这一页的过程中 ⇒ 写信号会**重入外壳渲染** ⇒ 切页时旧页面不被替换、被**追加**（卡片数 64 → 108 → 153 → …，真 DOM 验收 28 条失败）✗。机理与两条实测见 `docs/web/lite-framework.md` §3.4 |
| 子视图（`/tasks/<名>/config`） | 子组件的 `onMounted` 先于父页面跑 ⇒ 直接登记会被父页面盖掉（表现：在配置页点刷新，刷的是任务列表）✗ ⇒ 用 `queueMicrotask` 推到外层之后，卸载时把外层那份**还回去** ✓ |
| 没有转圈/置灰 | 外观要跟着页面的加载态实时变得靠信号 ✗（就是上面那条禁令）。所以不做：页面自己的 `load()` 幂等，重复点不会出问题 ✓ |

未变的：页面里那些**语境化**的刷新留着（例如直播页口令池卡片自己的「刷新」——
它读的是 `refreshPool()`，与整页 `load()` 不是一件事）。

### 2.2.3 窄屏（手机）上的两条硬约束（2026-10-01，用户实测逼出来的）

用户连报两件"宽屏上完全看不出来"的事，两条都已钉进 `node scripts/gates-web.mjs`
的**窄屏布局验收**（`web/lite/regress/narrow.mjs`，真按 375 宽开视口 ——
`interact.mjs` 是固定宽屏的，抓不到这一类）：

| 症状（用户原话） | 根因 | 规矩 |
|---|---|---|
| 账号行"这能看吗"：设备/凭据被挤成一列**竖排单字** | 文字列 `min-w-0 flex-1` 的 flex-basis 是 0，能被压到 40px，于是 `flex-wrap` **永远轮不到换行** | 一行卡片在窄屏必须**纵向分段**（名字+徽章 / 设备与到期 / 动作行），动作那行等分铺满（44px 触控高度）；宽屏才并成一行 |
| 添加弹窗"都没法点取消" | daisyUI 的 `.modal-box` 是 `max-height: 100vh`，而手机上 `100vh` **含地址栏**⇒ 底部在屏外；这弹窗又没有取消键，遮罩只剩顶上一缝 | 弹窗高度用 **`dvh`**；**标题栏 + ✕ 常驻不滚动**，只有内容区滚（`min-h-0 flex-1 overflow-y-auto`）；✕ 是"任何高度都够得着"的唯一出口 |

### 2.2.6 直播口令是**全实例共享资源**（2026-10-01）

用户口径原话：「口令需要共享，所有用户（本项目 mcloud 所有的用户下的所有移动云盘账号）
共享」；「一个 mcloud 用户只需要开一个 ws/小红书抓取，不要每个移动云盘账号都抓取」。

#### 池在哪、什么形状

`kouling-pool.json`，**实例级**（不是按用户/按账号）—— 放 `UserStore` 上只是复用
一个先例（新开 trait 会让 16 处测试替身各补一行空实现），语义上它属于**实例**。

```
{ cycleAtMs, codes: [{value, state, source, reason, firstSeenMs, validAtMs}],
  claims: { 账号 → { 口令 → 结论 } },          ← 防"同账号重复提交"
  lastLiveAtMs, gateClosedAtMs,                 ← 周期
  lastXhsAtMs, lastScrapeAtMs }                  ← 两道节流
```

#### 三态与那条**看着像矛盾**的规矩

`unknown` / `valid` / `invalid`。有效 **≥ 2** 就全场停止抓取（用户口径）。

> ⚠⚠ **过期 = 无效（行为的），但"要不要重听"是另一个问题。**
> `200118`（过期）在池里算**不可复用**；而 `rejected_kouling()` 对它必须仍返回
> `false` —— 否则每次过期都会触发一次毫无意义的 60 秒重听。
> 池问的是"这条还能不能再拿去用"；重听问的是"我是不是把口令认错了"。
> **谁把这两处合并，就会得到"要么不停重听、要么拿过期口令反复投"。**

状态跃迁只有**一个入口**：`settle_pool`（任务侧）。映射表：

| 领取结论 | 池里 |
|---|---|
| 成功 / **已兑换**（`200112`） | 有效（"口令本身是对的" ✓） |
| 口令错（`200108`） | 无效 |
| **过期**（`200118`） | 无效，**但 `reason` 留成"口令已过期"** |
| 别的业务码 | **不动**（本层没分类，不能当有效性判据） |

另外两条刻意的取舍：
* **有效只升不降** —— 验成有效之后别的账号再来只会得到"已领过"，不能把它退回未知
  （否则"够 2 条"会来回丢）。
* **已知无效的口令不许再进池** —— 弹幕里有人复读死口令，让它进池等于让"有效计数"
  永远凑不够 ⇒ 一直抓。这一条是"边听边领能停下来"的前提。

#### 写回池的**唯一**入口，以及为什么池写失败不算任务失败

池是"让别的账号少抓一次"的**优化**；本任务的价值是"把花领到手"。因为池写失败就把
已经领到的花判成失败，是拿优化否定目的 —— 而且那种失败最难查（日志里只有一句存储
错误，界面上是"任务失败"，可他明明领到了）。

> ⚠ **已知的并发窗口（刻意留着，不引锁）**：池是"读 → 改 → 存"，两个账号同时跑时
> 后写的会盖掉先写的一条备注。后果是"那条死口令下次再试一次"，**不是**文件损坏。
> 引一把进程内锁能消掉它，但会把池和进程生命周期绑在一起 —— 而池的意义恰恰是跨重启。

#### 抓取去重：为什么是**持久化时间戳**而不是进程内标志

90 秒窗口（[`SCRAPE_MIN_INTERVAL_MS`]），记在**动手之前**（收集要听满 60 秒，
抓完再记等于整个窗口都敞着）。用 `AtomicBool` 的两条都错：**重启就失效** ✗；
**并行测试会随机变红** ✗（谁把抓取"吃掉"取决于调度）。

> ⚠ 连"门最后是关的"也会记这个时间戳（是**故意**的）：效果是 90 秒内不再重复问门。
> 判定门结果一分钟内不会变，而"没开播"是这段里最正常的结局 —— 每个账号每分钟都打
> 两枪只是白喂风控。代价：开播最多晚 90 秒被发现。

#### 开门判据（三个条件的与）

```text
手里没有可用口令（含池里挑出来为空的）  且  池里有效 < 2 条  且  没开「只听手工」
        ⇒ 才开门去抓
```

⚠ 别改成"只要池里不够就抓"：手工口令是**小红书那条的唯一入口**（那条链没有可鉴权的
接口），而"门那两枪偶发失败"会把一趟**本来能跑完**的领取整体拖黄。它与共享并不冲突
—— 手工那几条**验证后也进池**（用户口径），池正是这么被填起来的。

#### 边听边领：**判据是"验出两条有效"，不是"收到两条"**（2026-10-02 已实现）

用户口径："在听的同时能够去领取，直接验证是否有效，**要的是两条有效的**"。

实现形状是任务里的一个**循环**：每轮 `听 → 立刻领取验证 → 回写池 → 再看够不够`。

> ⚠⚠ 这里换掉的是**判据本身**。原来是"**有口令被判无效**才重听" ✗ ——
> 于是"一条都没收到""收到两条全是没分类的码""只验出一条有效"这三种情况
> **一趟就结束了**，而它们恰恰是最该继续听下去的情形。
> 现在看的是**有效条数够不够 [`VALID_ENOUGH`]（2）**。

三条边界，缺一条就会变成"转圈"或"假收工"：

1. **每轮必须真的推进**：没收到新口令就结束 —— 否则同一批会被反复听、反复试；
2. **排除表逐轮累积**（含**第一次就成功的**）—— 否则下一轮会把同一批再领一遍，
   而同一账号对同一条正确口令的第二次请求回 `200112`，会污染归因、看起来像"口令坏了"；
3. **硬上限** `MAX_LISTEN_ROUNDS = 5` —— **弹幕是不可信输入**（观众发言也算候选口令），
   没有上限就是死循环。

> ⚠ **判据本地算，不回读池。** 池写失败是"只警告不失败"的（那是刻意的），
> 若判据靠回读池，写不进盘时就永远读到 0 ⇒ 循环一直转到硬上限。
> 起点取进门前的池快照，之后每轮把新验出的成功/已兑换并进一个集合（去重）。
> 这个 bug 是测试逼出来的：测试的替身存储不支持下写池，循环因此停不下来。

#### 场次：**日程不能跟着门一起丢**（2026-10-02）

界面上的「下一场几点」读的是**预告场**（`status == 0`）的 `expectStartTime` ——
而判定门只认 `status == 1` ⇒ **预告场与回放场必然被它筛掉**。
所以探测结果必须**整份留下来**（`KoulingPool::note_probe` / `ProbeRoom`），
只留门认可的那几间就等于把日历丢了。Go 参考实现的注释原话是「**日程不能跟着丢**」。

> ⚠ 类型名不叫 `ScheduleRoom`：core 里**早就有**一个 `schedule.rs`（那是**任务调度**），
> 两个"schedule"不同义 ⇒ 直播这边叫 `ProbeRoom`。

场次（`LiveSession`）的起止由观测推出：门开 ⇒ 开场；门关到过了宽限（＝周期翻篇）
⇒ 散场，而**散场时刻 = 最后一次看到它在播**，不是"发现它关了"那一刻 ——
后者会把我们没在看的那几小时也算成直播（门是按分钟抖动的）。

> ⚠ 「下一场」那个时间是**本地字符串，原样显示**：它没有时区，
> 解析成时间戳只会凭空造出一个错误的时刻。没有预告场时是 `None` 而**不是空串**
> —— 界面要能区分"没有下一场"与"上游没给时间"。

#### 历史页复用结构化明细（2026-10-02）

那套明细（领到的花 + 逐条口令落点）原来只长在直播页上 ⇒ **只有"当前这次"看得到** ✗，
历史里每一次直播都只剩一行小结。现在抽成 `web/src/ui/live-room-result.tsx`，
**直播页与历史页共用一份**。

> ⚠ 渲染判据是「**是直播任务 且 后端给了 `details.liveRoom`**」：光看 `task` 不够 ——
> 老记录只有文本小结，那时会渲染出一块"领到 0 个"的**假明细**，比不显示更糟。

#### 界面文案规范（从这次的"很奇怪的口径"里总结的）

那条被删掉的开关写着「获取口令但不领取（只获取口令并打印，不拿去领小红花）」——
一句话三种说法，而且**"打印"是 CLI 的词**（浏览器里没有这个动作）。三条规矩：

1. **UI 文案只描述界面里真实存在的东西**（没有"打印"）；
2. **不写实现细节**（"不进直播间" → "不听弹幕"）；
3. **校验结果在出错时说，不写进常驻标签**（"必须已填口令"不该常驻）。

> 一个需要括号自我解释的开关，本身就是它该被砍的信号。

### 2.2.5 任务页的形态（2026-10-01）

用户口径：**任务页保持简单，按分组处理，参数挪到单独的配置页**。

三件事：

1. **分组由后端给**。`TaskMeta` 现在带 `group` / `groupLabel`（`signin` / `live` /
   `app` / `device`）。任务页从前把签到族那 8 个任务名硬编码在前端当分组依据 ——
   而注册表才是权威，那份名单迟早漂移。**分组名也由后端给**（前端只决定"先看哪一组"）。
2. **任务页只做三件事**：分栏列出（标题 + 描述 + 任务名）、标出"可配置"、给一个「运行」。
   参数不在这一页填 —— 注册表里的任务只要有两个要参数，混在一起就没法一眼看完了。
3. **参数在 `/tasks/<任务名>/config`**。它不是第 10 条导航项（规范里侧栏 9 条封顶，
   配置页本来就属于「任务」）；`parsePath` 按**第一段**归属，所以它在 URL 上可直接进、
   侧栏仍高亮「任务」。`TasksPage` 自己盯着 `popstate` 换视图。
   ⚠ 2026-10-03 用户口径「先去掉#号」⇒ 路由从 `#/tasks` 改成 `/tasks`（干净路径）。
   跳转一律走 `web/src/ui/router.ts` 的 `navigate()`；**别自己写 `location.hash`**。
   代价与前提（服务端 SPA 回落、"末段带点会 404"）写在那个文件头部 ✓。

配套的后端（否则这一页只能是假的）：

| 接口 | 作用 |
|---|---|
| `GET /api/capabilities` | 每个任务带 `group` / `groupLabel` / **参数说明**（`name`/`title`/`kind`/`default`/`min`/`max`/`unit`/`help`） |
| `GET /api/tasks/{name}/config` | 读该任务的默认参数（缺省键**补成默认值**，前端不必自己算） |
| `PUT /api/tasks/{name}/config` | 存默认参数；**整体替换**，没给的键回落默认值 |

三条口径：

1. **存的是"默认参数"，不是"这一次的参数"**。任务页点「运行」时带上它；
   定时规则与编排步骤各带自己的 `body`，**不受影响** —— 一次运行收到什么参数，
   只取决于发起方，不取决于某个悄悄生效的全局默认值。
2. **校验在服务端**：前端照说明画表单，但拦不住 curl。类型、取值范围、
   "有没有这个参数"都在服务端判一遍；**不认识的键直接拒**（默默收下的表现是
   "填了没用"，那是最难查的一类）。
3. **从前 `params` 只有参数名**（`Vec<String>`），类型/默认值全靠前端猜。
   现在类型、默认值、范围一起给 —— 于是"参数表"只有一份，在前端不存在第二份。

### 2.2.4 设置页的形态（2026-10-01）

五块，每块**只写拿得到的东西**（拿不到的宁可不画 —— 摆一个点下去 404 的表单，
比没有更糟，因为用户会以为自己填错了）：

| 块 | 数据来自 | 能做什么 |
|---|---|---|
| **服务概况** | `GET /api/status` | 只读：调度器 / 运行时间 / 任务与定时/编排数 / 最近一次运行 |
| **账户安全** | `GET/PUT /api/admin/security`、`PUT /api/admin/password` | 改口令、口令下限、会话时长 |
| **存储信息** | `GET /api/system/storage` | 只读：数据目录 / 日志目录 / 二进制 / 占用 / 逐文件大小 |
| **服务操作** | `POST /api/system/restart` | 重启（确认框 + 起来之前轮询 `/api/status`） |
| **关于** | `GET /api/system/about` | 只读：版本 / 构建时间 / 提交 / **本次构建包含的改动** / 版权 |

设置页之外还有一处同批（2026-10-01）：**账号停用**。「停用」= 从各处**挑账号**的下拉里
消失，不是删除 —— 账号、凭据、历史全留着。实现是**一处收口**：
`GET /api/accounts` 默认只返回启用的，账号页显式 `?includeDisabled=true` 才拿到全部
（否则停用之后没法启用回来）。已存在的定时规则照旧跑：停用改的是"以后选谁"，
不是"过去的配置作废"。

**关于「检查更新」**：上游仓库是私有的（匿名访问 404），而这个服务在浏览器端没有任何
凭据去查发布 ⇒ **不做**那个按钮（摆一个必然失败的按钮，用户只会以为是自己网络的问题）。
那一栏给的是本机真拿得到的东西：构建时间、提交号、是否带着未提交改动、
以及**本次构建包含的最近 12 条提交**（构建期从 `git log` 抓下来写进二进制，
见 `crates/mcloud-server/build.rs` —— 运行期不需要仓库在场）。

三条口径值得记下来：

1. **改口令按"当前口令"验，不认身份**。会话被盗时这一条拦不住 —— 那是会话本身的语义
   （能改口令的会话本来就有全部权限）。真正的防护是**改完把该用户全部会话踢掉**，
   包括发起这次请求的那张，然后给当前浏览器换一张新的：
   一起踢出去的话，用户看到界面弹回登录页，只会以为"改失败了"。
   响应里的 `sessionsEnded` 用来说清"已让几处登录失效"。
2. **策略只影射未来**：口令下限对**之后设的口令**生效，会话时长对**之后新建的会话**生效。
   已发出的 cookie 不会被动缩短 —— 改设置就让人当场掉线，是最容易被骂的那种"贴心"。
3. **重启 = 优雅退出**，不是 `process::exit`：`main.rs` 的 `with_graceful_shutdown`
   走的是与 SIGTERM 完全相同的一段（停调度器 → 日志落盘），重拉交给 launchd/systemd。
   接口先回 `202`、300ms 后才发信号 —— 立刻发的话这一个响应本身会被截断，
   前端只看得到"网络错误"，分不清"重启了"还是"崩了"。
   所以前端在确认之后要**自己轮询 `/api/status`**，等到服务重新答话为止。

## 3. 参数从哪来：**配置文件，不是 flag**

mcloud 的 CLI 有 `--receive` / `--revive` / `--backup-gift` / `--multiple` /
`--prizes` / `--dry-run` … 十几个 flag。本项目的取向：

> **CLI 只给"跑哪一个"，参数在配置里。**

```
mcloud run sign 19900000000
        └─ 任务名         └─ 账号
```

参数（如 `skipKouling`）从 `data/tasks.json` 读：

```json
{
  "live-room": { "skipKouling": false }
}
```

**为什么**：flag 一多，"定时任务"与"手工运行"就会用**两套参数**
（一个来自 crontab 那行、一个来自 WebUI 表单），而它们必然漂移。
参数进配置后，三处（CLI / WebUI / 定时）读的是**同一份**。

| 维度 | mcloud | 本项目 | 理由 |

## 5.2 本轮修掉的三个真 bug（都源自 Vapor 的「setup 只跑一次」）

1. **认证闸写成顶层 `if (...) return <X/>`** ⇒ 那一刻 `authState` 还是
   `checking`，于是**永远返回转圈**。网络面板里 `/api/session` 明明回了 503、
   状态也确实变了，但界面不动 —— 不报错、不抛异常，只是"渲染决定被冻住了"。
   正确写法是把判断放进 JSX 表达式（`authGate()` 函数 + 三元）。

2. **侧栏那三行是 `const x = ...` 算好的值** ⇒ 同样是 setup 只求值一次，
   侧栏**永远**停在「正在问后端…」。同一文件里的 `themeToggle()` /
   `navLink()` 都是函数，就是这个道理。

3. **`probeSession` 成功路径没放行** ⇒ 带着有效 cookie 刷新页面会永远转圈。
   `request` 只在失败时推进状态（公开接口未初始化也回 200，所以"任何成功都放行"
   是错的），"放行"必须由**明确的认证动作**宣布。
