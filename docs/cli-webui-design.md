# CLI 与 WebUI 设计（重新设计）

> 本文是**重新设计**，不是对 mcloud 的移植。
> 参考 mcloud 的目的是**避开它踩过的坑**，而不是复刻它的形态。

---

## 0. 一句话

**WebUI 为主，CLI 只管「无头也能跑」的那几件事。**

判断标准只有一条：

> 这件事**需要人看着**吗？
>
> - 需要 ⇒ WebUI（扫码、填验证码、看日志、抢兑）
> - 不需要 ⇒ CLI（定时触发、刷新凭据、跑一条配好的链）

mcloud 的 CLI 有 **40+ 个子命令**（`login qr/sms/smid show/reset/refresh`、
`user init/list`、`migrate`、`fixture extract`、`live-room`、`capabilities`、
`auth refresh`、`signin` 一族带十几个 flag…）。本项目**不要那么多**：
多数子命令是"开发期工具"或"WebUI 能做的事在终端又做了一遍"，
而重复入口的代价是**两处都要改**。

---

## 1. CLI：5 个命令，不多不少

```
mcloud login    qr | sms <手机号> | app <手机号> | password   登录账号（交互）
mcloud run      <任务名> <账号>            跑一次任务
mcloud cron     <定时id>                  跑一条定时（供外部 crontab 调用）
mcloud auth     refresh <账号|--all>      刷新 auth 凭据
mcloud pipeline run <编排id>              跑一条编排
```

> `login app` 与 `login sms` **并列而不是合并**：App 端走另一套密钥、
> 另一套设备头，请求体还要 AES 加密 + 末 10 位错位，落盘的 `auth`
> 前缀也不同（`mobile` vs `pc`）。做成 `sms --app` 会让"我登的是哪一端"
> 在命令行上不可见，而端一旦搞错，产物是**错的身份** —— 之后每个任务
> 请求都会带着它发出去。

外加两个无副作用的：

```
mcloud tasks                              列出可用任务
mcloud --version / --help
```

### 为什么是这五个

| 命令 | 为什么 CLI 需要它 |
|---|---|
| `login` | 扫码/短信**必须在没有 WebUI 时也能做**（首次部署、服务器上） |
| `run` | 排障：某条任务单独跑一次看输出，不必开浏览器 |
| `cron` | **外部 crontab 的入口**。见下 |
| `auth refresh` | 凭据将过期时批量续期，脚本里最常调的一个 |
| `pipeline` | 一条链手工重跑（WebUI 挂了或想看清退出码） |

### `cron` 的语义：**外部触发，CLI 不常驻**

```
# crontab
0 8 * * *  /usr/local/bin/mcloud cron daily-sign >> /var/log/mcloud.log 2>&1
```

- CLI **不**跑调度循环、**不**长驻。时间由系统 crontab 管。
- `cron <id>` 只做一件事：按 `schedules.json` 里那条配置跑一次，然后退出。
- 退出码：成功 `0`、任务失败 `1`、**配置错误 `2`**。

**为什么不让 CLI 常驻调度**：常驻就意味着要处理"进程挂了""两个实例同时跑"
"重启后补不补错过的点"—— 而这三件事在 mcloud 的 server 里已经有完整答案
（水位线、错过策略、并发闸）。CLI 再实现一份就是**两处语义**，
而它们的表现差异极难发现（一个补跑、一个不补）。

> ⚠️ **两者不要同时跑同一条定时。** 水位线是"读→判→写"，不是跨进程的原子认领。
> server 在跑调度时，外部 crontab **不应**再触发同一条。这一点在
> `cron` 的启动日志里明确打印警告。

### **不做**的事（刻意）

| 不做 | 理由 |
|---|---|
| `schedules add/rm` | 定时是"配置"，**改配置文件或 WebUI**。CLI 里再做一个 CRUD 是第三个入口 |
| `pipelines add/rm` | 同上 |
| `user init/list` | 单用户工具，不需要用户管理子命令 |
| `migrate` | 没有旧库要迁移 |
| `fixture extract` | 开发期工具，不该进用户 CLI |
| `login smid show/reset` | 设备指纹是内部状态，用户改它只会搞坏账号 |
| 十几个 `--flag` | 参数走**任务自己的配置**，见 §3 |

**"不需要支持编排"** 按你的原话落地成：CLI **没有** `pipeline create/edit` ——
只有 `pipeline run <id>` 跑已有的。编排的增删改在 WebUI 或直接改
`data/pipelines.json`。

## 2. WebUI：登录闸 + 6 个页面

### 2.1 登录闸（跟随 mcloud）

第一道门是 **WebUI 自己的用户名/口令**，与"账号登录"是两件事：

| | 谁的凭证 | 存哪 | 谁用 |
|---|---|---|---|
| **WebUI 登录闸** | 你设的一个用户名/口令 | `users` 表（argon2id PHC 串） | 浏览器 |
| **账号登录** | 移动云盘的 auth | `accounts.json` | 任务运行时 |

- 首次访问 ⇒ `/api/setup` 引导建管理员。**建之前其他接口一律 503**。
- 口令用 **argon2id**（`m=19456, t=2, p=1, out=32`）—— 与 mcloud 同参数，
  这样两边金标向量可以对拍。
- 会话是**服务端 session**（不是 JWT）：`HttpOnly` + `SameSite=Strict` cookie，
  登出即失效。

> **为什么本地工具也要这道闸**：服务器的监听地址是可配置的
> （`MCLOUD_ADDR`）。今天图省事跳过认证，明天有人 `0.0.0.0` 一开，
> 整个网盘权限就挂在公网上。这道闸是**唯一的**边界，不能靠"应该只监听本地"。

### 2.2 页面

| 页面 | 职责 | 优先级 |
|---|---|---|
| **登录/初始化** | 首次建管理员、登录、登出 | P0 |
| **账号** | 账号列表、**添加账号（弹窗：扫码/短信/手机端/账密/凭据）**、编辑（昵称/设备号/凭据）、移除 | P0 |
| **总览** | 调度器状态、今日运行 / 账号凭据 / 定时与编排 / 网盘遗留、最近运行（见 §2.2.1） | P0 |
| **任务** | 任务列表 → 选账号 → 运行 → 实时日志 → 中止 | P1 |
| **定时** | 定时 CRUD、启停、下次执行时间 | P1 |
| **历史** | 运行历史 + 日志回看 | P1 |
| **设置** | 实例信息、并发上限、通知渠道 | P2 |

**编排页保留完整 CRUD。** 这一条我最初设计成"只读"，**是错的** ——
需求里明确写了 WebUI 要含「定时与编排 CRUD」。已按需求落地：

| | CLI | WebUI | 配置文件 |
|---|---|---|---|
| 定时 | 只能跑（`cron <id>`） | **完整 CRUD** | 可直接编辑 |
| 编排 | 只能跑（`pipeline run <id>`） | **完整 CRUD** | 可直接编辑 |

**收敛的方向是 CLI，不是 WebUI。** 我先前把"CLI 不做编排增删"错读成
"WebUI 也不做"，那会让编排彻底没有图形入口 —— 而需求说的是
"CLI 不需要支持编排，有需要直接改配置文件"，主语是 **CLI**。

判据回到 §0 那条：**这件事需要人看着吗？**
编排的创建要填步骤、选账号、设 `continue_on_error` —— 那需要看着，
所以它属于 WebUI。而 CLI 是无头场景，给它一堆 flag 才是重复入口。

### 2.2.1 总览页的形态（2026-09-30 重新设计）

一屏四段，从上到下回答四个问题：

| 段 | 回答什么 |
|---|---|
| **引擎条** | 定时调度在不在跑、当下有没有任务在跑、下一次自动运行是**哪一条**定时 |
| **四张指标卡** | 今日运行（成功 / 失败 / 跳过）、账号凭据（到期）、定时与编排、网盘遗留 |
| **最近的定时任务 + 今日AI豆**（并排 2:1） | 左边：接下来几条各**还有多久**跑、上次跑成什么样；右边：**每个账号**今天AI豆进出多少 |
| **最近运行** | 最近 **5 条** + 一个「查看全部」入口 |

**命名口径**：界面上写「AI豆」（现行叫法），不写「云朵」—— 后者只出现在
**引用上游接口名**的地方（`cloudRecordV2` 那条流水）。见 `docs/conventions.md` §5.5。

**记账口径（2026-09-30，需求方点出）**：AI豆**按账号各记一本账**，
**不做跨账号合计** —— 加出来的"总AI豆"哪个账号都用不了（豆不能跨账号花）。
所以那张卡是一个账号一行；哪天想"优化"成一个总数，先回来看这一句。

两条口径写在这里，免得下次又被"顺手加一格"：

- **指标卡那四格只用现有接口能拿到的数**（`/api/status`、`/api/runs`、
  `/api/schedules`、`/api/accounts`）—— 没有为它新增任何后端字段。
  派生规则（"今日"取本地 0 点、7 天内到期算"将到期"、谁的 `nextFireAt` 最小）
  全部在 `web/src/pages/dashboard-page.tsx` 里以纯函数形式给出，一眼可复核。
- **收敛到 5 条**：原先总览把 `/api/runs` 的全部记录（后端上限 100 条）铺成一张表，
  于是它成了第二个历史页，第一屏被表格顶下去 —— 而"一眼看清现状"正是这一页的
  全部意义。看全量细节是历史与日志页的事。

⚠ **「今日AI豆」那一格是唯一的例外**：它**要一个后端还没有的端点**
（`GET /api/beans/today`，由云朵记录汇总）。前端已按契约定稿，端点未落地时
它显示「待接入」；缺什么、口径怎么定，见 `docs/task-inventory.md` §5。

⚠ 另记一条**没做**的：数据**年龄**由页头的「更新于 22:31」承担，
这一页**不轮询** —— 自刷会让人以为那个时间戳在动，其实只是又采了一次样。

### 2.2.2 账号页的形态（2026-10-01 重构）

用户口径：「添加账号可以用新路由或者弹窗唤出而不是常驻」+「账号只有移除没有编辑」
+「通过添加 auth 创建新账号未实现」，要求仍是**简单、明了、功能全而言简意赅**。

| 区块 | 内容 |
|---|---|
| 页头 | 「账号」标题 + 刷新 + **添加账号**（按钮，打开弹窗） |
| 账号列表 | 一行一个账号：昵称（回落掩码手机号）、设备号、凭据到期、平台徽章；右侧 **编辑** / **移除** |
| 添加账号（弹窗） | 客户端形态（Windows/macOS）+ 五条路：扫码 / 短信 / 手机端 / 账号密码 / **凭据** |
| 编辑账号（弹窗） | 昵称、设备号、**换凭据**（留空 = 不改；pc 凭据才出现形态选择） |
| 本机设备指纹 | 机器级（扫码的 `dID`），保留在页面底部 —— 它不是"某个账号"的属性 |

三点判断：

1. **弹窗而不是新路由**。导航项上限是硬约束（§2.1 那条：9 项是上限），
   而且"添加账号"是**在一个页面里完成的一件事**，不是一个新的目的地 ——
   新路由会多一个需要返回的页面，弹窗不需要。四条登录路径的表单本身
   300 多行，常驻会把"我有哪几个账号"压到第一屏之外，而那句话才是主语。
2. **凭据从不出现在界面上**。「编辑」里那格永远是空的输入框：服务端也从不回显它
   （列表 DTO 里没有 `auth`）。所以编辑是 **PATCH（给了才改）**，
   而不是像设置那样的"整体替换" —— 否则改个昵称也得重新粘一遍凭据。
3. **一个账号一份读数**这条同样适用（AI豆那张卡，见 §2.2.1）。

### 2.2.3 窄屏（手机）上的两条硬约束（2026-10-01，用户实测逼出来的）

用户连报两件"宽屏上完全看不出来"的事，两条都已钉进 `node scripts/gates-web.mjs`
的**窄屏布局验收**（`web/lite/regress/narrow.mjs`，真按 375 宽开视口 ——
`interact.mjs` 是固定宽屏的，抓不到这一类）：

| 症状（用户原话） | 根因 | 规矩 |
|---|---|---|
| 账号行"这能看吗"：设备/凭据被挤成一列**竖排单字** | 文字列 `min-w-0 flex-1` 的 flex-basis 是 0，能被压到 40px，于是 `flex-wrap` **永远轮不到换行** | 一行卡片在窄屏必须**纵向分段**（名字+徽章 / 设备与到期 / 动作行），动作那行等分铺满（44px 触控高度）；宽屏才并成一行 |
| 添加弹窗"都没法点取消" | daisyUI 的 `.modal-box` 是 `max-height: 100vh`，而手机上 `100vh` **含地址栏**⇒ 底部在屏外；这弹窗又没有取消键，遮罩只剩顶上一缝 | 弹窗高度用 **`dvh`**；**标题栏 + ✕ 常驻不滚动**，只有内容区滚（`min-h-0 flex-1 overflow-y-auto`）；✕ 是"任何高度都够得着"的唯一出口 |
| 五个方式 tab 挤到边、「手机端」折成两行 | `join` 是内容宽度，五个标签在 375 下只剩 2px 余量 | 窄屏 `join w-full` + 每格 `flex-1`、`px-2`、`whitespace-nowrap`；四字的「账号密码」缩成「账密」；宽屏维持原样（`md:w-auto` / `md:flex-none` / `md:px-4`） |

**仍未做的**（择出来记着，别当成已实现）：

- **每账号设置**（任务开关、推送渠道）：后端 `GET/PUT /api/accounts/{id}/settings` 早就通了，
  界面也已落地（同页的设置弹窗，2026-10-01 与这次重构同期）。
- **换凭据只能粘贴**。上游的 `POST /user/auth/refreshToken` 有 CLI（`mcloud auth refresh`），
  没有 HTTP 路由，也没有按钮 —— 而它需要 `user_domain_id`，导入的账号恰恰没有。
- **设备号不能"重新生成"**。只能手填（有个"换一台设备"是**机器级**的，
  改的是扫码用的 `dID`，与账号的设备号不是一回事 —— 这两件事在界面上必须分得开）。

## 3. 参数从哪来：**配置文件，不是 flag**

mcloud 的 CLI 有 `--receive` / `--revive` / `--backup-gift` / `--multiple` /
`--prizes` / `--dry-run` … 十几个 flag。本项目的取向：

> **CLI 只给"跑哪一个"，参数在配置里。**

```
mcloud run sign 19900000000
        └─ 任务名         └─ 账号
```

参数（如 `dryRun`）从 `data/tasks.json` 读：

```json
{
  "sign": { "dryRun": false }
}
```

**为什么**：flag 一多，"定时任务"与"手工运行"就会用**两套参数**
（一个来自 crontab 那行、一个来自 WebUI 表单），而它们必然漂移。
参数进配置后，三处（CLI / WebUI / 定时）读的是**同一份**。

## 4. 与 mcloud 的关键差异（不是抄，是取舍）

| 维度 | mcloud | 本项目 | 理由 |
|---|---|---|---|
| CLI 命令数 | 40+ | **5** | 多数是开发期工具或 WebUI 的重复入口 |
| 调度 | server 常驻 | server 常驻 + **CLI 单次触发** | 两种部署形态都要能用 |
| 参数传递 | 大量 flag | **配置文件** | flag 会与 WebUI 表单漂移 |
| 编排编辑 | WebUI 有完整编辑器 | **只读**（改文件） | 最复杂的一页，日常不改 |
| 包体 | Go 单二进制 | Rust 单二进制 | 同 |

## 5.1 本轮实测证据

前端认证闸用**真实浏览器**（Edge + CDP）走完了五态，量的是"界面真的换了没有"：

| 状态 | 结果 |
|---|---|
| 未初始化 | 显示「首次使用，请创建管理员账号」+ 三个输入框，无侧栏/dock |
| 初始化后 | **自动进入外壳**（侧栏 7 项 + dock），无需再登录一次 |
| 已初始化未登录 | 显示「请登录以继续」，无侧栏/dock |
| 口令错 | 留在登录页，报**后端原文**「凭证无效：用户名或口令错误」 |
| 口令对 | 进入外壳 |

CLI 的退出码逐条实测：

| 调用 | 退出码 |
|---|---|
| `cron`（无参数 / 不存在的 id） | `2` |
| `cron daily-sign`（错过太久，弃掉） | `0`（"不该跑"是正常，退 0 免得监控天天假警） |
| `auth refresh`（无参数 / `--lead-days 0` / 账号不存在） | `2` |
| `auth refresh --all`（还剩 83 天，未打上游） | `0` |
| `auth refresh --all`（`expire < 0`，需人工） | `1` |

## 5.2 本轮修掉的三个真 bug（都源自 Vapor 的「setup 只跑一次」）

1. **认证闸写成顶层 `if (...) return <X/>`** ⇒ 那一刻 `authState` 还是
   `checking`，于是**永远返回转圈**。网络面板里 `/api/session` 明明回了 503、
   状态也确实变了，但界面不动 —— 不报错、不抛异常，只是"渲染决定被冻住了"。
   正确写法是把判断放进 JSX 表达式（`authGate()` 函数 + 三元）。

2. **侧栏那三行是 `const x = ...` 算好的值** ⇒ 同样是 setup 只求值一次，
   侧栏**永远**停在「正在问后端…」。同一文件里的 `themeToggle()` /
   `navLink()` 都是函数，就是这个道理。

3. **`probeSession` 成功路径没放行** ⇒ 带着有效 cookie 刷新页面会永远转圈。
   `request` 只在失败时推进状态（公开接口未初始化也回 200，所以"任何成功都放行"
   是错的），"放行"必须由**明确的认证动作**宣布。
