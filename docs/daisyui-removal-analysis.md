# 移除 daisyUI、改用纯 Tailwind —— 一份量出来的分析

> **口径**：用户下达的是「我准备移除 daisyUI，用 tailwind 直接写，**分析一下**」
> ⇒ 这份文件只做取舍与实测，**本轮没有改任何生产代码**（`web/src/app.css` 我一个字节都没写 ✓
> —— 它此刻正被另一条工作线改着，见 §7）。
>
> **一句话结论**：真要移除，**净省 2,301 B gzip**（CSS 12,892 → 10,591，**−17.9%**），
> 但这 2,301 B 里**有 1,524 B（66%）不用移除 daisyUI 就能拿到** ——
> 一行 `exclude` 清单（649）+ 自写一个 20 行的 `collapse`（875）。
> 剩下 **777 B** 才是"卸掉依赖"本身的价格，而它买回来的不是字节，是**整套主题令牌层与
> base 行为从此归本仓维护**。⇒ **建议先吃前两块，把"移除"留到哪天主题层想大改时一起做。**

## 1. 怎么复现（一条命令，跑完自己还原）

```bash
cd web && node scripts/daisyui-size-probe.mjs        # 实测 6.3 s（6 次全量构建 + 自检）
```

它把 `src/app.css` 读进内存 ⇒ 在内存里派生五个变体 ⇒ 每个变体写到**临时文件**
`src/__daisy_probe.css`，用一份**继承真 `vite.config.ts`** 的临时配置把**整个 app** 重构建一遍
（只把 `src/main.ts` 那句 `import './app.css'` 顶到探针文件）⇒ 跑完删临时文件，
再用真 app.css 重建一次 `dist`，保证产物与源码对齐 ✓。**全程不碰 `src/app.css`。**

> ⚠ 为什么"必须构建整个 app"：`@tailwindcss/vite` 的候选类名是**沿模块图**扫的。
> 第一版探针只构建那一份 CSS，于是 `src/pages/*.tsx` 一条都没进扫描 ⇒
> 探针 V0 比真实构建**少 2,661 B raw**（65,855 vs 68,516），差的就是页面真正用到的那批 utility。
> 现在自检是**逐字节比对**（不只是同长度），当前输出：
> `真实构建 raw=68600 gzip=12892 ／ 探针 V0 raw=68600 gzip=12892 ⇒ 逐字节一致 ✓`。
>
> 加 `--dump` 会把每个变体的**产物 CSS** 留到 `web/.daisy_probe_dump/V*.css`，
> 用来回答"这两个变体到底差在哪几行"—— 只比字节数会看不出机制（§3 那条就是这么查出来的）。

**两个口径说明**（都实测过）：
① gzip 用 **node zlib −9**；同一份文件（本轮 V0 产物）拿 python 的 `gzip.compress` 量读成
**12,878** —— 比 node 少 **14 B**，差的是 **deflate 实现**、不是内容。
表里所有 Δgzip 出自**同一轮、同一工具**，所以可以互相减。
② 脚本自己放在 `web/scripts/` 里**不污染读数** —— 实测挪走再构建，CSS 的 hash 与 raw 字节完全一致。
（Tailwind 4 扫源码**原文**，脚本里那些类名形状的字符串本来会生成死 CSS，这次逐字节核过 ⇒ 没有。）

## 3. 现状：daisyUI 其实已经只剩三层东西

普查 `web/src`（**303 个**不同的 class-position token；`class=` 位置收割，见脚本注释）之后，
它现在承担的是：

1. **主题令牌**：两个 `@plugin "daisyui/theme"` 块给 light/dark 各一份 `--color-*`，
   外加形状令牌（`--radius-box/field/selector`、`--border`、`--size-field`、`--depth`、`--noise`）。
2. **Tailwind 颜色 utility 的注册**（⚠ 最反直觉的一条，见 §4）。
3. **base 层三点**：`:root` 的底色/正文色（`--root-bg`）、`scrollbar-color`、
   还有那套滚动锁 —— `--page-scroll-lock` / `--page-overflow` / `:root:not(span){overflow:…}` /
   `--page-has-backdrop`。**本仓 app.css 有两处在写它**（`.drawer` 与窄屏抽屉那节，
   `--page-scroll-lock: ;`），也就是**已经耦合上了**。

而**组件层它基本已经不参与了**：`@plugin "daisyui"` 的 `exclude` 挡住了 32 个名字，
app.css 的 `@layer components`（约 1,200 行）是**本仓自己写的** —— 实测
**V0/V6/V5/V1 四个变体里这一层都是 27,762 B 一字不变**，即 daisyUI 在组件层一个字节都没付。
（V4 是 27,235 B，**少 527 B** —— 别当成回归，见下面那条。）

剩下的 30 个组件里，**页面真在用的只有 `collapse` 一个**（`filter` 被算成"在用"是**已知假阳性**：
`class={…${filter.value…}` 里的**标识符**也会被收进 token；这个方向是**保守**的 ⇒ 只会少排、
不会把真在用的排掉）。其余 28 个是**纯白付**：daisyUI 的组件是**整块发**的、不按用量裁剪，
所以"没用也付钱"是机制，不是 bug。

> **V4 那 −527 B 是什么**（`--dump` 逐行 diff 查出来的，顺带记一条构建期行为）：
> 自写 `@theme` 把 `--color-*` 的值写进了 `:root` ⇒ lightningcss 认为它**静态可读**，
> 于是把本仓那批 `color-mix(in oklab, var(--color-base-content) 20%, transparent)` 的
> **降级兜底那一条**折成字面色（实测 `.status` 从 `var(…)` 变 `#18181b33`），
> 而 `@supports (color:color-mix…)` 里那条**照旧是 var 引用**（两块计数 45 没动）⇒
> 支持 `color-mix` 的浏览器（= 本项目全部目标）**仍然随主题换色**，只有不支持的老浏览器
> 拿到冻在浅色的那版。⇒ 这是**省字节**，不是深色主题 bug；但迁移时要知道它发生过。
> （对照读数：产物里 `var(--color-` 出现次数 V0 175 → V4 139，正是被折掉的那 36 处。）

## 4. 两个**静默**坑（这是本次分析最该记住的东西）

**① 颜色 utility 不是主题块注册的，是主插件注册的。**
把 `@plugin "daisyui"` 删掉、两个 theme 块照留（V1），产物里这 **14** 个页面在用的类**一起消失**：
`bg-base-100` `text-primary` `bg-base-200` `border-base-300` `border-base-200` `text-error`
`text-warning` `text-primary-content` `divide-base-200` `bg-primary` `rounded-field` `rounded-box`
+ collapse 一族（探针最后一行直接列出清单，是**从产物反查**的，不靠人脑点）。
⇒ "只删组件层"这个直觉是**错的**；不补 `@theme` 就等于把上百处样式抹掉，
而且**不报错、类型也过**（和 app.css 顶部那条 `.tab` 被 exclude 挡掉的事故同一类）。

**② `collapse` 这个类名和 Tailwind 4 自带的 utility 撞了。**
Tailwind 有 `collapse` 这个 utility（把元素判成"折叠不可见"），
daisyUI 的组件一直用一条 `visibility:revert-layer` 顶着它。
⇒ 一旦不引 daisyUI 的 collapse 组件、又没人显式写 `visibility:visible`，
那 4 处 `<details class="collapse">` **整块内容直接看不见** ——
不是"样式变丑"，是内容消失。探针的"同名撞车"那几行就是量这个的：
V5/V1 报 `**内容会消失**`，V4 因为原型里写了 `visible` 才报 ok。
⇒ 真要自写，**顺手把类名换成不撞的 `disclosure`** 比补一条 `visible` 更彻底。

## 5. 移除后要接手的东西（清单）

* **主题令牌层**：`@theme { --color-* / --radius-* }` 一份 + `[data-theme="dark"]` 覆盖一份。
  原型见 `web/scripts/daisyui-size-probe.mjs` 里 `TOKEN_LAYER`（~100 行，含 3 个语义块 + collapse）。
  ⚠ **两份必须成对写** —— app.css 的注释里已经记了两次真实事故：
  只写 light 那半 ⇒ 深色掉回默认色（用户拿截图报过"粉红删除按钮"）；
  只写颜色不写 `-content` ⇒ 深绿底压深绿字，徽章糊成一团。
* **base 三点**：`:root` 底色/正文色、`scrollbar-color`、滚动锁那一套（§3 第 3 条）。
* **`collapse`**：~20 行（含 §4② 那条护栏）。
* **门禁重新定格**：窄屏布局验收与真 DOM 验收（`node scripts/gates-web.mjs --full`，≈77 s）
  要在新 CSS 上跑一遍；逐像素比对的旧基线不能再当判据。
* **WCAG 读数不用重算**：只要令牌值逐条照抄现产物（原型就是这么做的），
  app.css 注释里那批对比度读数继续成立。
* **未来想用某个组件**（tooltip / dropdown / kbd / footer / link …）：今天它是
  **从 `exclude` 删一个名字**，移除后是 **自己写一份**。这条是长期税，不是一次性的
  —— 现在白付的那 28 个里有 26 个就是"哪天可能想用"的存货。

## 6. 不在字节里的代价

按仓库那条秤（`AGENTS.md`：「框架不够用时把"改框架"和"绕开"摆上秤」）称一下：

* 字节侧：**−2,301 B gzip（首屏 −8.2%）**。其中 **1,524 B 属于"绕开"就能拿到的**
  （一行 exclude + 20 行 collapse），且不碰主题体系。
* 归属侧：多养一套令牌层 + base 行为 ≈ 100 行，**且每次调品牌色要改两个主题块** ——
  这正是现在注释里被反复提醒的那条纪律，只是从今天"少踩就少错"变成"没踩就是没写"。
* 心智侧：确实少一个依赖、少一层"它到底发了什么"的疑问；但 app.css 已经有
  ~1,200 行自建组件，**这层心智模型其实早就在了** —— 移除带来的增量没有想象中大。

⇒ **推荐顺序**：① 现在就做 V6（−649 B，风险 0）；② 顺手自写 collapse 并把类名改成
`disclosure`（再 −875 B，改 3 个文件）；③ 只剩 **777 B** 的"完全移除"，
等哪天要动品牌色/主题体系时**一并做**，别为它单独开一次全量重定格。

> ⚠ 但①②要**等 app.css 这条工作线收口**再做 —— 它现在是脏文件（240 增 / 66 删未提交），
> 往里加 `exclude` 名字会把别人的改动一起定格。
