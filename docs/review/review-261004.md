## 0. 结论速览

**整体**：这是一份**相当扎实**的代码库 —— 分层铁律（`core ← crypto/upstream/store ←
engine ← tasks ← app ← server`）没有破口、密码学有黄金向量逐字节钉住、`unsafe_code = "forbid"`
实测 0 命中、运行期三档门禁（fmt / clippy / 1849 条测试）本轮复跑全绿、Release 与 CI 可核对。
问题分两类，**都不是"结构烂"，而是两类很具体的失血**：

1. **"失败被写成功"与"该回滚的没回滚"**：副作用链（上传文件、兑换、打卡）里的错误被
   兜成默认值、或早退路径漏掉收尾 ⇒ 用户的网盘/账目上留下不该留下的东西，而报告说成功。
2. **文档与装置落后于代码**：改名（两 bin 合一）、换前端栈（Vue → lite）、`../mcloud`
   身份变化都没同步到 README/usage/AGENTS，其中 `docs/usage.md` 是 **Release 正文链接过去
   的那份**，新用户照着敲就是 `No such file`。

**最该先动的 8 件**（跨线合并，下面 §2 有证据与建议）：

| # | 编号 | 一句话 | 为什么排前面 |
|---|---|---|---|

## 2. 最要紧的 8 条（跨线合并）

### 2.1 `co-1` [高·仅静态/中] 落盘既不原子也不耐久，还可能**同时**毁掉备份

`crates/mcloud-store/src/json_store.rs:329` 的 `write_atomic` 没有 `fsync`；
`read_json:368` 把 0 字节文件当成"没有数据 ⇒ 用默认值"；而 `:331` 在覆盖前 copy 出的
`.bak` 会被**这一次写入**顺手覆盖。三者叠起来：掉电/崩溃落在"文件已截断、内容未落盘"的
窗口时，读回的是"空 ⇒ 默认值"，**且**唯一的备份已被这次空写覆盖 ⇒ 账号、会话、口令池
一起消失而没有任何报错。这在"个人自用、掉电不常见"的定位下不是每天发生，但**一旦发生不可逆**，
建议优先修（`fsync` 文件 + 目录、空文件按损坏处理并保留上一份 `.bak`）。

### 2.2 `up-1` [高·仅静态/高] `exist` 兜成 `false` —— 唯一会删到用户文件的那条不变量

`crates/mcloud-upstream/src/app_cloud_upload.rs:745-747`（`:707` 同）把字段级的
`exist` 做 `unwrap_or(false)`；`crates/mcloud-tasks/src/task_expansion.rs:517/:611`
拿它决定"这个 `fileId` 能不能进清理名单"。`exist == true` 的语义是**撞上用户本来就有的同名文件**
（上游把**它的** `fileId` 交回来）⇒ 兜成 `false` 就是把这个 id 当自己的产物删掉。
注释自己写着这里 false 也危险，但运行期没有任何可断言的位置。建议：字段读不到 ⇒
**不做清理**（保守侧），并把"读不到"写进 `problems`。

### 2.3 `tk-2` / `tk-3` [高·仅静态/高] 上传产物回收只挂链尾，取消与异常早退都漏

`crates/mcloud-tasks/src/app_task.rs:1218` 是全链**唯一**的 cleanup；循环内
`:1045/:1181` 的 `check_cancelled()?` 会直接绕过它；且 `upload_one_file`（`:1308-1330`）
在 `create` 成功、`PUT`/`complete` 失败时把已拿到的 `file_id` 丢掉 ⇒
文件永久留在用户网盘根目录。`task-expansion`、`ai-avatar` 同型；artifact 账本是 run 维的，
全仓没有 reaper。对照 `task_expansion.rs:523` 的做法（**提前落账**）才是正解。

### 2.4 `sv-1` [高·仅静态/高] 并发闸早退不解取消登记 ⇒ 两个表永久泄漏

见 §1 的复核。`run_owners`/`CancelRegistry` 各漏一条且永不回收，「正在运行 N 个」
只涨不跌；**双击「运行全部」**（第二次撞并发闸）就能触发。改法一行：早退前
`self.cancel.release(run_id)`（照抄上一条早退的写法）。

### 2.5 `tk-1` [高·仅静态/高] `acted` 两套口径 ⇒ "报成功"与"上游认账"是两件事

`app_task.rs:1108`（434：要上游计数真涨）/ `:1203`（上传、埋点：只要写请求发成功），
而同一个文件 `:1383` 自己记着真机 106 的读数：`clicked:true` 而上游 `state` **恒 `WAIT`**。
`task_outcome()` 仍返回 success。⇒ 用户看到"成功"，账号上什么都没发生。
至少要让"未获上游确认"在 outcome 里可见（如 `partial` + 明细标记），而不是 success。

### 2.6 `sv-2` [高·仅静态/高] 调度器把任务同步 `await` 在 tick 里

`scheduler.rs:312` 的 `fire(...).await` 在 tick 循环内；一条跑 >60s 的任务会让同一时刻
其它定时落进 `Decision::Missed` ⇒ **整体弃掉**（`:297-305`，只留一条 warn）。
用户侧表现是"某天那个定时没跑"。建议 fire 起 spawn、水位线单独推进。

### 2.7 `up-2` [高·仅静态/高] 直播 WS 握手无超时

`crates/mcloud-upstream/src/live_ws_client.rs:319` 的 `connect_async` 没有 timeout，
`:399` 的 deadline 在 connect **成功之后**才起算，调用侧
`crates/mcloud-tasks/src/live_room.rs:961` 直接 `await` ⇒ 握手黑洞时任务永久挂起，
界面上像"正在听"。加 `tokio::time::timeout` 即可。

### 2.8 `dc-1` [高·已实测/高] `docs/usage.md` 整篇还在叫 `mcloud-server` / `mcloud-cli`

16 处旧名（`:7 :9 :10 :50 :51 :79 :92 :108 :119 :122 :148 :167 :176` …），而
`crates/mcloud-server/Cargo.toml:17-19` 只有一个 `bin mcloud`、`release.yml:411` 的
Release 正文写着「包内**只有一个可执行文件 `mcloud`**」、`:423` 的"完整说明"链接**就是这份文档**。
⇒ 下载 Release 的人按 `./mcloud-server` / systemd `ExecStart=…/mcloud-server` 全部起不来。
同族还有 `README.md:186-190`、`docs/conventions.md:743` 的 `--bin mcloud-cli`（照抄即报错）。
